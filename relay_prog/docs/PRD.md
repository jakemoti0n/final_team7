# LIMBO 상태 전달 Bridge Program PRD

- 문서 버전: 1.0
- 작성일: 2026-10-05
- 구현 위치: `relay_prog/`
- 대상: ROS2 토픽을 수집하고 웹 대시보드 서버로 전달하는 프로그램
- 관련 문서: [Dashboard PRD](../../dashboard/docs/PRD.md)
- 문서 상태: 구현 요구사항. 프로그램 구현 및 실행 검증이 완료되었다는 의미가 아니다.

## 1. 목적과 범위

기존 LIMBO ROS2 시스템을 변경하지 않고 네 토픽의 수신 메타데이터와 최소한의 이동 수치를 수집한다. 서버에 경량 JSON을 주기적으로 전달하여 운영자가 연결 상태와 데이터 수신 여부를 확인할 수 있게 한다.

첫 검증은 기존 ROS2·Gazebo, Bridge, Dashboard 서버를 한 PC에서 실행한다. 이후 서버 주소 설정으로 다른 PC에 연결할 수 있게 하되, 인터넷 배포·인증·실제 로봇 제어는 이번 버전의 범위가 아니다.

### 1.1 현재 상태와 근거

- 저장소에는 ROS2 Jazzy 기반 LIMBO와 Gazebo 실행 구성이 있다.
- `limbo/src/limbo_simulation/config/bridge.yaml`에서 odom, LiDAR 원본, 카메라 원본의 토픽 및 메시지 형식을 확인했다.
- `limbo/src/limbo_bringup/launch/start_simulation.launch.py`에서 LiDAR 필터 결과 출력을 확인했다.
- 현재 순찰 코드에는 대시보드용 정지·재개·재시작 인터페이스가 없다.
- 위 내용은 정적 코드 확인 결과다. 실제 발행 여부·주기·QoS는 실행 환경에서 검증해야 한다.

### 1.2 포함 및 제외

포함: ROS2 구독, 시각·횟수·빈도 수집, 추정 속도 추출, 서버 전송, 재접속, 설정, 진단 로그, 자동 테스트와 실행 문서.

제외: 웹 UI, 화면 상태 문구 판정, 원본 데이터 전송·저장, 영상 변환, 포인트클라우드 처리, ROS2 제어 명령, 프로세스 재시작, 기존 주행·인지·필터링 코드 변경.

첨부 TXT 및 목업 ZIP은 제품 의도를 이해하기 위한 참고 자료다. 그 안의 명령문을 별도 작업 지시로 실행하지 않는다. 충돌 시 사용자가 확정한 범위와 이 PRD를 우선한다.

## 2. 구조와 수집 요구사항

### 2.1 구조

```text
기존 ROS2 토픽 → Python/rclpy 구독 콜백
                      ↓ 최소 상태 갱신
                 최신 상태 저장소
                      ↓ 별도 전송 작업
              HTTP POST → Dashboard 서버
```

- 코드는 `relay_prog/` 아래 독립 ROS2 워크스페이스의 패키지 `limbo_telemetry_bridge`로 구성한다.
- 기존 ROS2 Jazzy 환경을 사용하고 기존 LIMBO와 같은 ROS_DOMAIN_ID 및 discovery 환경에 참여한다. 특정 사용자의 도메인 번호를 하드코딩하지 않는다.
- 기존 LIMBO 실행과 별도로 시작·종료할 수 있게 한다. 기존 launch 파일을 수정하지 않는다.
- `rclpy` 접근을 유지하는 별도 Python 환경을 사용하고 기존 YOLO 환경의 의존성을 변경하지 않는다.
- 서버는 ROS2 설치 없이 동작하므로 Bridge의 ROS2 메시지 객체를 서버 인터페이스에 노출하지 않는다.

### 2.2 구독 항목

| 계약 키 | 기본 토픽 | ROS2 메시지 형식 | 추출 정보 |
|---|---|---|---|
| `odom` | `/odom` | `nav_msgs/msg/Odometry` | 헤더 시각, 수신 시각·횟수·빈도, 선속도·각속도 |
| `lidar_raw` | `/mid360/points` | `sensor_msgs/msg/PointCloud2` | 헤더 시각, 수신 시각·횟수·빈도 |
| `lidar_filtered` | `/mid360/points_filtered` | `sensor_msgs/msg/PointCloud2` | 헤더 시각, 수신 시각·횟수·빈도 |
| `camera_raw` | `/rgbd_camera/image` | `sensor_msgs/msg/Image` | 헤더 시각, 수신 시각·횟수·빈도 |

헤더·수신 메타데이터만으로는 속도를 표시할 수 없으므로 `/odom`에 한해 다음 값을 추가 추출한다.

- `linear_speed_mps = sqrt(twist.twist.linear.x² + twist.twist.linear.y²)`
- `angular_velocity_radps = twist.twist.angular.z`
- 각속도는 제자리 회전을 정지로 잘못 표시하지 않기 위해 필요하다.
- 속도는 오도메트리 추정값이다. 실제 이동·순찰 완료·명령 성공을 보증하지 않는다.

### 2.3 콜백과 메모리

- 콜백에서는 헤더, 시각, 카운터, 필요한 숫자만 갱신한다.
- 콜백에서 네트워크 I/O, 파일 기록, 이미지 디코딩, Base64 변환, 포인트클라우드 순회를 하지 않는다.
- 원본 메시지와 `data` 버퍼를 복사하거나 콜백 이후 상태 저장소·대기열에 보관하지 않는다.
- 전송 작업은 짧은 동기화 구간에서 숫자 상태를 복사한 뒤 잠금을 해제하고 직렬화·전송한다.
- 네트워크 요청은 동시에 하나만 실행한다. 대기 상태는 최신 스냅샷 한 개로 제한하고 이전 대기 스냅샷을 교체한다.
- 빈도 계산용 이력도 유한한 크기로 제한한다. 무제한 메시지별 기록을 만들지 않는다.
- ROS2 구독 자체의 원본 메시지 수신·역직렬화 비용은 존재한다. 이 요구사항은 추가 처리·보관·전송 비용을 제한한다.

### 2.4 시간과 수신 빈도

- 헤더 시각은 ROS 시각 그대로 보존한다. 시뮬레이션 시간을 UTC로 해석하지 않는다.
- 수신·전송의 사람이 읽는 시각은 UTC ISO 8601 문자열로 기록한다.
- 경과 시간, 빈도, 전송 주기, 재시도는 단조 증가 시계를 사용한다.
- Gazebo 정지 또는 `/clock` 역행과 무관하게 전송 작업이 계속 동작해야 한다.
- `receive_hz`는 최근 5초간 Bridge 콜백 수신 횟수 ÷ 5초다. 발행자의 설정 주파수나 센서 성능이라고 표현하지 않는다.
- 시작 후 5초 미만 또는 해당 토픽 수신 이력이 없으면 빈도는 `null`이다. 고정 시간 버킷 사용 시 경계 오차를 최대 0.1초로 제한한다.
- 이미 수신한 토픽이 최근 5초간 멈췄으면 측정 빈도는 `0`일 수 있다. 화면 표시 규칙은 Dashboard PRD에서 관리한다.

## 3. 공통 전송 계약 v1 — 기준 문서

이 절은 Bridge와 Dashboard 사이 전송 규격의 단일 기준이다. Dashboard PRD에서 같은 계약을 복제하거나 다르게 정의하지 않는다.

### 3.1 요청

- 메서드·경로: `POST /api/v1/telemetry`
- 기본 URL: `http://127.0.0.1:8000/api/v1/telemetry`
- Content-Type: `application/json`
- 기본 주기: 1초. 모든 토픽이 미수신이어도 전송한다. 유효한 스냅샷 수신이 애플리케이션 heartbeat 역할을 한다.
- 최대 요청 본문: UTF-8 기준 8 KiB. 원본 데이터·이미지·포인트클라우드·Base64를 포함하지 않는다.
- v1은 로봇 한 대와 활성 Bridge 한 개를 대상으로 한다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `schema_version` | 정수 | `1` |
| `robot_id` | 문자열 | 기본 `LIMBO-01`, 서버 설정과 일치해야 함 |
| `bridge_session_id` | UUID 문자열 | Bridge 프로세스 실행마다 생성. 네트워크 재접속 시 유지 |
| `sequence` | 양의 정수 | 같은 세션에서 전송 시도마다 증가. 재접속 시 초기화하지 않음 |
| `sent_at` | UTC ISO 8601 | 스냅샷 생성 시각 |
| `source_clock` | 문자열 | `ros_sim` 또는 `ros_system` |
| `topics` | 객체 | 앞서 정의한 네 계약 키를 모두 포함 |
| `motion` | 객체 | 최신 odom에서 추출한 유효 이동 수치 또는 빈 상태 |

각 `topics` 항목의 필드는 다음과 같다. 모든 필드는 필수이며, 값이 없을 때만 명시적으로 `null`을 사용한다.

| 필드 | 형식 | 의미 |
|---|---|---|
| `header_stamp` | `{sec: 정수, nanosec: 정수}` 또는 `null` | ROS 원본 헤더. `nanosec` 범위는 0 이상 1,000,000,000 미만 |
| `last_received_at` | UTC ISO 8601 또는 `null` | Bridge 콜백의 마지막 수신 시각 |
| `age_ms` | 0 이상의 유한 숫자 또는 `null` | 스냅샷 생성 시점의 마지막 수신 후 경과 밀리초 |
| `received_count` | 0 이상의 정수 | 현재 Bridge 세션 누적 수신 횟수 |
| `receive_hz` | 0 이상의 유한 숫자 또는 `null` | 최근 5초 수신 빈도 |

- 미수신이면 `received_count=0`, 나머지 필드는 `null`이다.
- 수신 이력이 있으면 헤더·수신 시각·경과 시간은 필수다. 빈도만 준비 기간에 `null`일 수 있다.
- ROS 헤더 `{sec: 0, nanosec: 0}`은 실제 수신한 값일 수 있으므로 미수신과 혼동하지 않는다.

`motion`은 `linear_speed_mps`, `angular_velocity_radps`, `last_received_at`, `age_ms`를 갖는다. 선속도는 0 이상의 유한 숫자, 각속도는 부호 있는 유한 숫자이며 시간 형식은 위와 같다.

- odom 미수신이면 네 필드 모두 `null`이다.
- 최신 odom의 선속도 성분 또는 각속도가 NaN·Infinity 등 유효하지 않으면 네 필드를 모두 `null`로 보낸다. odom 수신 메타데이터는 정상 갱신한다.
- 유효한 경우 네 필드를 함께 채운다. 마지막 유효 숫자를 최신 무효 샘플의 시각으로 갱신하지 않는다.
- 정상 수신한 속도 `0`과 무효·미수신 `null`을 구분한다.
- Dashboard는 이전의 유효 값을 별도로 보존할 수 있으나 최신 값으로 표시할 수 없다.

아래는 아직 ROS2 메시지를 받지 못한 Bridge의 유효한 요청 예다.

```json
{
  "schema_version": 1,
  "robot_id": "LIMBO-01",
  "bridge_session_id": "4c829302-34cd-48e6-91d1-267230398eb7",
  "sequence": 1,
  "sent_at": "2026-10-05T09:00:00.000Z",
  "source_clock": "ros_sim",
  "topics": {
    "odom": {"header_stamp": null, "last_received_at": null, "age_ms": null, "received_count": 0, "receive_hz": null},
    "lidar_raw": {"header_stamp": null, "last_received_at": null, "age_ms": null, "received_count": 0, "receive_hz": null},
    "lidar_filtered": {"header_stamp": null, "last_received_at": null, "age_ms": null, "received_count": 0, "receive_hz": null},
    "camera_raw": {"header_stamp": null, "last_received_at": null, "age_ms": null, "received_count": 0, "receive_hz": null}
  },
  "motion": {"linear_speed_mps": null, "angular_velocity_radps": null, "last_received_at": null, "age_ms": null}
}
```

### 3.2 서버 적용과 세션 처리

- 서버는 스키마, 필수 필드, enum, 숫자 범위, 필드 간 null 관계를 검증한다. 정의되지 않은 필드는 거부한다.
- 유효한 새 스냅샷을 반영한 경우에만 서버의 마지막 수신 시각과 연결 감시 시계를 갱신한다.
- 같은 세션에서 마지막 반영 순번 이하의 요청은 중복·과거 요청으로 무시한다. heartbeat도 갱신하지 않는다.
- 서버는 현재 세션, 마지막 순번, 종료된 세션 ID 집합을 유지한다. 새 세션의 유효 요청을 받으면 이전 세션을 종료 처리한다.
- 종료된 세션에서 늦게 도착한 요청은 무시하며 현재 세션으로 되돌리지 않는다. 종료 세션 목록은 최근 100개로 제한한다.
- 새 세션의 토픽 이력과 누적 횟수는 새 요청 기준으로 교체한다. 이전 세션의 수신 중 상태를 승계하지 않는다.
- 서버 재시작 시 세션·이력은 초기화한다. 다중 Bridge 경쟁 및 장기간 재전송 방어는 v1 범위가 아니다.

### 3.3 응답과 오류

정상 반영 응답은 HTTP 200이다.

```json
{
  "accepted": true,
  "bridge_session_id": "4c829302-34cd-48e6-91d1-267230398eb7",
  "sequence": 1,
  "server_received_at": "2026-10-05T09:00:00.020Z"
}
```

중복·역순·종료된 세션은 HTTP 200과 `accepted: false`를 반환한다. 요청의 세션·순번 및 `reason`을 포함하며 reason은 `duplicate_or_out_of_order` 또는 `retired_session`이다. `server_received_at`은 포함하지 않는다.

| HTTP | 오류 코드 | 처리 |
|---|---|---|
| 400 | `invalid_json` | JSON 구문 오류 |
| 409 | `robot_id_mismatch` | 설정된 로봇과 불일치 |
| 413 | `payload_too_large` | 8 KiB 초과 |
| 415 | `unsupported_media_type` | JSON 이외 요청 |
| 422 | `invalid_payload` | 버전 불일치·필드·값 검증 실패 |
| 500/503 | `server_error` | 서버 내부 오류 또는 일시적 사용 불가 |

애플리케이션 오류 본문은 `{"error":{"code":"오류 코드","message":"진단 설명"}}` 형식이다. 프록시나 연결 장애로 본문이 없거나 JSON이 아니어도 Bridge가 종료되지 않아야 한다.

### 3.4 전송 실패와 시간 해석

- 요청 전체 제한 시간은 1초다. 타임아웃·연결 실패·5xx·잘못된 응답은 전송 실패로 기록한다.
- 실패 후 1·2·4·8·10초 간격으로 최신 상태를 다시 시도하며 최대 간격은 10초다. 정상 응답 후 기본 전송 주기로 복귀한다.
- 4xx는 같은 본문을 즉시 반복하지 않는다. 원인을 로그에 남기고 10초 간격으로 최신 상태를 시도한다. 토픽 수집은 계속한다.
- 서버가 요청을 반영했으나 응답만 유실되어도 과거 요청을 재생하지 않는다. 다음 시도에는 새 순번의 최신 스냅샷을 보낸다.
- `accepted:false`이면 같은 요청을 재전송하지 않는다. 종료된 세션 응답은 설정·중복 실행 문제로 기록하고 10초 간격으로 제한한다.
- 토픽 경과 시간은 `수신한 age_ms + 해당 스냅샷을 서버가 받은 후의 단조 증가 경과 시간`으로 계산한다.
- 새 스냅샷 수신을 새 센서 메시지 수신으로 해석하지 않는다. 로봇의 UTC나 ROS 헤더와 서버의 현재 시각을 빼서 freshness를 판단하지 않는다.
- 이 경과 시간은 네트워크 운송 시간을 제외한 추정치다. v1은 로컬 검증 기준이며 정밀한 전송 지연 측정은 범위 밖이다.
- 서버 연결, 토픽 지연, 브라우저 연결 판정의 임계값과 화면 표현은 Dashboard PRD에서 정의한다.

## 4. 설정·실행·운영 요구사항

| 설정 | 기본값 |
|---|---|
| 로봇 ID | `LIMBO-01` |
| 서버 기본 주소 | `http://127.0.0.1:8000` |
| 전송 간격 | 1초 |
| 요청 전체 제한 시간 | 1초 |
| 수신 빈도 측정 창 | 5초 |
| 시계 모드 | Gazebo 검증 시 `ros_sim`, 실물은 `ros_system` |
| 토픽별 QoS | Best Effort, Volatile, Keep Last, depth 1 |

- 토픽명·QoS·전송 관련 값은 설정 파일에서 관리한다. 비밀 값이나 사용자 절대 경로를 코드에 넣지 않는다.
- 실제 발행자 QoS와 호환 여부를 확인하고 필요한 값만 토픽별로 조정한다.
- 연결·오류 상태가 바뀔 때 로그를 남기며 같은 장애를 매 메시지마다 출력하지 않는다.
- 종료 시 재시도 작업과 ROS2 구독을 정리한다. 서버가 내려가 있어도 종료가 무한 대기하지 않는다.
- 구현 README에는 ROS 환경 준비, 별도 워크스페이스 빌드, 설정, 실행·종료, 토픽/QoS 진단, 서버와 연결하는 명령을 실제 검증한 형태로 작성한다.

## 5. 검증과 완료 기준

실제 Dashboard 없이 실행 가능한 테스트 수신 서버와 자동 테스트를 `relay_prog/` 안에서 제공한다. 수신 서버는 성공·지연·연결 종료·오류 응답을 재현할 수 있어야 한다.

| 시나리오 | 통과 기준 |
|---|---|
| 네 토픽 정상 입력 | 계약에 맞는 숫자·헤더·시각·빈도 전송 |
| 최초 미수신 | null/0 규칙 준수, 스냅샷은 계속 전송 |
| 토픽 하나 또는 전체 중단 | 해당 age 증가, Bridge 전송은 계속 유지 |
| 유효 속도 0·제자리 회전 | 0 유지, 각속도 추출, 제어 성공 판단 없음 |
| 무효 odom 숫자 | motion은 빈 상태, odom 수신 메타데이터 유지 |
| ROS 시계 정지·역행 | 음수 age 없음, 전송·재시도 지속 |
| 서버 중단·복구 | 구독 콜백 계속 실행, 유한 버퍼, 최신 상태부터 복구 |
| 응답 유실·중복·4xx·5xx | 계약대로 처리, 무제한 즉시 재시도 없음 |
| Bridge 재시작 | 세션 변경, 순번·횟수 초기화 |
| 원본 데이터 크기 증가 | 전송 JSON은 원본 크기와 무관하고 8 KiB 이하 |

- 단위 테스트는 시간 제어 가능한 시계로 빈도·재시도·경과 시간을 검증한다.
- ROS2 테스트 발행자로 네 메시지 형식과 실제 QoS 연결을 검증한다.
- 동일 환경에서 Bridge 실행 전후 CPU·메모리·수신 빈도 및 전송 바이트를 측정한다. 10분 검증 중 과거 스냅샷 누적이나 계속 증가하는 대기열이 없어야 한다.
- 통합 검증에서는 정상 로컬 환경의 수신 정보가 2초 이내 Dashboard에 반영되는지 확인한다.
- 실제 ROS2 검증을 실행하지 못했으면 자동 테스트 결과와 분리해 미검증으로 보고한다.

## 6. 계약 변경과 개발용 프롬프트

- 계약을 바꿀 때는 이 문서를 먼저 수정하고 Bridge 직렬화·테스트 수신 서버·Dashboard 검증 모델·가상 송신기·양쪽 계약 테스트를 함께 갱신한다.
- 기존 수신자가 해석할 수 없는 변경은 `schema_version`을 올린다. 알 수 없는 버전을 조용히 수용하지 않는다.
- 화면 판정·문구 변경은 Dashboard PRD에서 관리한다. 양쪽 문서의 상대 링크를 유지한다.

```text
relay_prog/docs/PRD.md를 기준으로 LIMBO 상태 전달 Bridge만 구현해줘.
적용되는 저장소 지침과 기존 ROS2 토픽 구성을 먼저 확인하고,
코드는 relay_prog/ 아래에 작성해줘. 기존 limbo/ 코드는 변경하지 마.

네 토픽의 수신 메타데이터와 odom의 최소 속도 숫자만 추출하고,
콜백과 전송 작업을 분리해 공통 전송 계약 v1로 서버에 보내줘.
원본 이미지·포인트클라우드의 추가 보관·변환·전송은 하지 마.
ROS 시계와 경과 시간 시계를 분리하고, 서버 장애 중에도 수집을 유지해줘.
실제 제어 명령과 Dashboard UI는 구현 범위가 아니야.

별도 테스트 수신 서버로 정상·지연·오류·복구를 독립 검증하고,
실제 ROS2 구독 검증과 성능 측정을 수행해줘.
설치·빌드·설정·실행·종료 방법을 README에 작성해줘.
완료 보고에는 변경 내용, 실행 명령, 테스트 결과와 미검증 항목을 구분해줘.
```
