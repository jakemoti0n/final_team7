# 컨트롤러 재비교: MPPI(지금) vs RPP (2026-10-14, 메인 PC)

## 왜 다시
10-12 비교(`experiments/2026-10-12_controller_mppi_vs_rpp/`)는 옛 설정(전역 STVL 15 s, HumanLayer 220, 두 사람 복도)이었다. 오늘 채택 설정(치명 사람 비용, 비켜 주는 사람, `prune_distance` 2.5, 카메라 0.7 m·0°)에서 같은 벤치로 1회씩 다시 봄. 젯슨 오린 나노에서 MPPI 계산량(10-12: 컨트롤러 CPU 27 % vs 2 %)이 문제될 때의 선택지를 미리 갖기 위해.

## 조건
- 커밋 `4dd827d`, 기본 BT, `run.sh`. RPP 설정은 `tools/sim_trials/apply_controller.py rpp`(속도 한계 MPPI와 같음 0.6 m/s·1.8 rad/s, 후진 금지)
- 비켜 주는 사람 복도(`people2`), 홀 손님(`hall`), 낮은 상자(`box`) 각 1회. MPPI 기준값은 같은 날 같은 설정의 `pl_navfn_corridor`·`pl_navfn_hall`(계획기 비교)·`cam0_box`(카메라 0°)

## 해석
- 10-12와 달리 RPP도 다 완주했다. 그때 중단은 두 사람이 복도를 물리적으로 막은 장면이었고, 지금 벤치는 비켜 주는 사람이라 RPP의 약점(스스로 안 피함)이 안 드러난다
- 그래도 성격은 같다. RPP는 열린 홀·상자에서 10~18 % 빠르고, 사람이 정면에서 오는 복도에서는 복구 5·경로 변경 15로 멈추고 다시 계획하기를 반복한다. 상자는 MPPI보다 가깝게 붙는다(0.11~0.21 m)
- 사람 거리·충돌은 둘이 같다(HumanLayer 치명 비용이 둘 다에 작용)

## 결론
- **MPPI 유지.** 복도에서 멈춤·재계획이 적고 장애물 여유가 크다
- 젯슨에서 MPPI 주기 경고가 실제로 나오면 먼저 `batch_size`·`time_steps`를 줄이고, 그래도 안 되면 RPP가 대안이다. 이 표가 그때 기준
