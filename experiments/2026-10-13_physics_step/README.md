# 물리 스텝 1 ms vs 2 ms: 실시간 비율과 odom 정확도 (2026-10-13, 노트북)

## 왜 했나
시연 화면에서 로봇이 너무 느려 보였다. 재 보니 Gazebo 실시간 비율(RTF)이 0.6이라 MPPI 실속 0.4 m/s가 화면에서는 0.24 m/s로 보이는 것이었다.
병목은 gz 서버 메인 스레드(물리, 1 ms 스텝 = 시뮬 1초에 1,000번 계산)가 한 코어를 포화하는 것. 스텝을 2 ms로 늘리면 계산이 반으로 주는데,
"바퀴 계산이 거칠어져 정확도가 떨어지지 않나"를 숫자로 확인하기 위해 비교했다.

노트북 i5-14450HX(16코어), 가구 학원 월드 `aischool_2f_furnished`, 커밋 26f790e. 2 ms는 install 폴더에 임시 사본(`max_step_size` 0.002)을 만들어 썼고 저장소 월드는 안 바꿨다.

## 1. 실시간 비율 (speed_probe.py: /clock 대 벽시계)

| 조건 | RTF |
|---|---|
| 1 ms, Gazebo 화면 켬 (시연 상태) | 정지 0.62, 주행 0.60 |
| 1 ms, 화면 끔 (RViz만) | 정지 0.78, 주행 0.71~0.74 |
| 1 ms, 화면·RViz 모두 끔 | 0.87 |
| 2 ms, 화면 끔 (RViz만) | 정지 0.97, 주행 0.91~0.96 |

gz 서버 CPU 150%, 그중 메인 스레드 88%. gz gui 프로세스는 210%를 더 쓴다. gz gui만 PID로 끄면 서버까지 같이 종료되므로 화면은 처음부터 `gui:=false`로 띄워야 한다.

## 2. 순찰 1회 비교 (patrol_node, aischool_furnished_waypoints.yaml E→G→J, phys_record.py + phys_compare.py)

| 항목 | 1 ms | 2 ms |
|---|---|---|
| 완주 | E·G·J 도착 | E·G·J 도착 |
| 주행 시간 (시뮬 s) | 197 | 203 |
| 정답 경로 길이 (m) | 65.3 | 65.4 |
| 최고 속도 (m/s) | 0.47 | 0.46 |
| 속도 추종 오차 odom−cmd 평균 (m/s) | 0.004 | 0.003 |
| 0.1 s 이동량 오차 평균 / 최대 (mm) | 2.4 / 9.2 | 2.5 / 9.1 |
| 바퀴 odom 누적 위치 오차 최종 (m) | 3.0 | 4.6 |
| EKF(/odometry/filtered) 누적 오차 최종 (m) | 1.1 | 1.2 |

누적 오차는 둘 다 크고 2 ms가 더 크지만, 시간대별로 보면(drift_timeline.py) 오차가 뛰는 곳은 둘 다 제자리 회전 구간이고 직진 중 이동량 오차는 같다.
순찰은 매번 경로·회전량이 달라(누적 회전 1,800° vs 1,885°) 이 차이는 스텝 때문이 아니라 회전 횟수 차이다. 그래서 통제 시험을 했다.

## 3. 통제 시험 (drive_test.py: /cmd_vel 직접, 직진 0.4 m/s 15 s → 제자리 1.0 rad/s 5바퀴, drive_compare.py)

| 구간 | 항목 | 1 ms | 2 ms |
|---|---|---|---|
| 직진 5.9 m | odom − 정답 이동량 | 0.0 mm | −8.0 mm (0.14 %) |
| 제자리 5바퀴 | 정답 회전 | 1631° | 1635° |
| 제자리 5바퀴 | odom 회전 | 1782° | 1786° |
| 제자리 5바퀴 | odom − 정답 | +150.5° (9.2 %) | +150.4° (9.2 %) |

(뒤이은 후진·역회전 구간은 회전이 명령 1,800°에 못 미쳐 로봇이 가구 쪽을 보게 됐고 후진 중 부딪혀 두 경우 모두 오염됐으므로 뺀다.)

## 결론
- **1 ms와 2 ms의 정확도 차이는 측정 한계 안**이다. 직진 6 m에 8 mm, 제자리 5바퀴 회전 오차는 소수점 첫째 자리까지 같다. 속도 추종·최고 속도도 같다.
- 정확도 문제는 스텝이 아니라 **제자리 회전 때 바퀴 odom이 9 % 더 돈다고 세는 것**이다(두 스텝 모두). 원인은 실린더 바퀴가 제자리 회전할 때 옆으로 미끄러지는 Gazebo 특성으로 보인다. 플러그인의 wheel_separation 0.54·radius 0.075는 URDF와 같다. 순찰 중 바퀴 odom이 3~4 m 틀어지는 이유이며, EKF(IMU 포함)가 1 m, AMCL이 그 위에서 보정하므로 주행에는 문제가 없다. 실제 로봇도 제자리 회전 odom은 믿지 않는 편이 맞다.
- 적용: bookstore(이미 3 ms) 빼고 월드 7개 `max_step_size` 0.002 (커밋 (30)). 적용 후 화면 켠 상태 RTF: 정지 0.92~0.98, 주행 0.95 (1 ms 때 0.60), odom 최고 0.44 m/s.
