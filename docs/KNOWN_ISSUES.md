# 알려진 문제

시뮬레이션과 코드 점검 중에 발견했지만 아직 고치지 않은 문제를 모은다.
고치면 이 표에서 지우고 커밋 메시지에 남긴다.

마지막 갱신: 2026-10-13 (v14가 사람 앞에서 느려진 걸 막힘으로 오판해 복구 반복 — 원인 좁힘)

## 바퀴 헛돎 감시

| 문제 | 근거 | 영향 | 대책 후보 |
|---|---|---|---|
| 사람이 로봇 가까이 지나가면 헛돎으로 잘못 판단 (팀원 환경에서 반복) | 스캔 두 장을 맞추는 ICP가 벽 대신 같이 움직이는 사람에 맞춰 "로봇이 안 움직였다"고 계산하는 것으로 추정. 시뮬레이션에서 본 오탐은 1번(`SLIP: wheel 0.22 m, scan 0.01 m`)뿐이고, 사람 경로·`human_test_world`(사람 10명)·스캔 지연 0.5초 재현에서는 0번이라 **재현 못 함** | 주행이 취소됨 → 2026-10-12부터 `cancel_navigation_on_slip: false`로 임시로 끔 (감지·로그는 유지) | 팀원 환경의 `SUSPECT`/`SLIP` 로그 줄과 `ros2 bag record /scan /odom /ground_truth/odom /wheel_slip` 녹화로 원인 확정. 2026-10-12 방어 수정: 바퀴 odom과 스캔 시각 맞춤, 확정까지 2초(0.5초 × 4) 연속, 두 스캔 일치 비율 0.8 미만이면 판단 보류. 팀원 환경에서 오탐이 사라지는지 확인 후 취소를 다시 켤지 정함 |
| 진짜로 막혔을 때 주행을 취소할지 정해야 함 | 로봇이 상자에 막혀 바퀴만 돈 경우는 감지가 맞았음. **취소를 끈 상태에서는 상자를 2분 동안 계속 밀었음**: Nav2의 "10초간 진전 없음" 판단이 바퀴 odom을 보는데, 헛도는 동안 바퀴 odom은 계속 앞으로 감 | 지금(취소 끔)은 진짜로 막혀도 로봇이 멈추지 않음. 헛도는 동안 바퀴 odom이 쌓여 위치 추정도 틀어질 수 있음 | 오탐을 고친 뒤 취소를 다시 켜기, 또는 취소 대신 정지·경고 (팀 논의) |

## 센서 배치 (프로토타입 45×45×70cm, 결정 필요)

| 문제 | 근거 | 영향 | 대책 후보 |
|---|---|---|---|
| 사람 몸이 박스 가운데 영역의 25%보다 적으면 거리가 배경까지로 나옴 | `depth.percentile: 25`. 다리를 크게 벌리거나 옆모습이면 다리 사이 배경이 75%를 넘을 수 있음. 하반신 모델 + 25%에서 멈춤 구간 예측의 16%(35/217)가 1m 넘게 틀림 | 그 순간 사람 위치가 뒤로 밀려 human_layer cost가 사람 뒤에 깔림 | percentile 10~15 비교, 하반신 모델의 `leg` 박스로 거리 재기, depth에서 가장 가까운 덩어리 찾기 |
| 하반신 모델을 기본으로 쓸지 | 시뮬레이션에서 다리만 보이는 사람 검출 65% → 100% (위 TROUBLESHOOTING). 실제 사람으로는 확인 안 함 | 지금은 기존 yolo11n이라 2m 안 사람 검출이 끊김 | 실제 로봇 시점 사진으로 확인 후 `limbo_perception`에 넣고 `yolo.model` 변경 |
| 2m 안의 사람은 카메라에 다리만 보여 YOLO 검출이 끊김 | 카메라(시뮬레이션) 0.5m 높이·수평. OAK-D Lite 컬러 세로 시야 54°라 1m 앞은 약 1.0m 높이까지만 보임. `aischool_2f_scenarios`에서 1.6m 앞에 멈춘 사람의 YOLO 신뢰도 0.05~0.6, 기준(0.3) 미만이 1~2초씩 이어짐 | 로봇 바로 앞 사람을 가장 못 봄 (1m 정지 기능 거리). 검출이 끊기면 추적 ID가 바뀌고 예측이 비어 human_layer cost가 사라짐 | 0.7m 높이에 위로 10°면 1m 앞 1.45m(가슴)까지, 15°면 1.6m까지 보임. 대신 카메라가 가까운 바닥을 못 봐서 낮은 장애물은 다른 센서가 맡아야 함 |
| MID-360 아래쪽 시야가 −7°라 가까운 낮은 물체를 못 봄 | 0.725m 높이·수평. 바닥은 5.9m, 0.1m(방지턱)는 5.1m, 0.3m는 3.5m, 0.5m는 1.8m보다 멀어야 보임. STVL `voxel_decay`가 1초라 멀리서 본 낮은 물체를 다가가는 동안 잊음 | 낮은 장애물·방지턱·연석에 부딪힐 수 있음. 지금은 수평 카메라가 1m부터 바닥을 메우지만, 카메라를 위로 기울이면 사라짐 | LiDAR를 앞으로 기울이기 (20°면 바닥 1.4m부터, `/scan`을 중력 기준으로 자르고 STVL 시야 각도도 수정 필요), STVL 기억 시간 늘리기, 범퍼 높이 근거리 센서(ToF·초음파, 마이크로컨트롤러로 모아 collision monitor에 연결) |
| 시뮬레이션 카메라 시야가 실제와 다름 | 시뮬레이션 가로 71.6°(1.25rad), 실제 OAK-D Lite 컬러 가로 69° | 시뮬레이션이 실제보다 조금 넓게 봄 | 센서 배치를 정할 때 `horizontal_fov`를 1.204로 맞춤 |

## 시뮬레이션·월드

| 문제 | 근거 | 영향 | 대책 후보 |
|---|---|---|---|
| 시작할 때 Nav2 lifecycle이 시간 초과로 안 뜸 (가끔) | `human_test_world`에서 AMCL Configuring 멈춤, 순찰 반복 중 10회 중 1~2회 `map_server/change_state` 시간 초과 → AMCL 활성화 실패 → global costmap이 `map → base_link` TF를 못 받아 Nav2 실패. **원인 추정**: `start_simulation.launch.py`가 위치 추정을 8초, Nav2를 11초에 고정 시간으로 띄워서 초기화가 늦은 회차에 순서가 꼬임 ([10회 검증](NAV2_YAW_10_RUN_VALIDATION_2026-10-12.md)) | 시뮬레이션을 다시 띄워야 함 | 고정 시간 대신 map server·AMCL이 active이고 TF가 준비된 뒤 Nav2 시작. 반복 시험용으로 RViz를 끄는 launch 인자 |
| `human_test_world`는 정사각형 방이라 스캔만으로 방향 구분이 안 됨 | (0,0)에서 0°/90°/−90°/180° 모두 스캔 일치 94~95% | Pose Estimate를 손으로 찍으면 크게 틀리기 쉬움 (실제로 두 번 다 틀림: 일치 9%, 4%) | 초기 위치는 `amcl.yaml` 값 사용 (적용 완료) |
| `aischool_2f`는 피난안내도 사진 기반 근사 | 축척은 교실 깊이 실측(약 6.1m, 보폭 기준)과 복도 폭(약 1.5m)으로 맞춤. 문은 0.9m로 통일 | 벽 위치 오차 수십 cm 가능 | 실측 치수를 더 받으면 `tools/aischool_2f/build_mask.py`에서 보정 |
| 이전에 녹화한 rosbag 두 개는 Pose Estimate가 틀린 상태 | 스캔-지도 일치 9%, 4% | 그 bag으로 Nav2 성능을 비교했다면 결과를 다시 봐야 함. person_detector 비교는 카메라 기준이라 영향 없음 | 새로 녹화 |

## 코드 (리뷰에서 발견, 미수정)

| 문제 | 위치 | 영향 |
|---|---|---|
| YOLO를 카메라 15Hz 매 프레임 콜백 안에서 실행, costmap은 5Hz로만 사용 | `limbo_perception/person_detector.py` `image_callback` | 예측의 약 2/3가 쓰이지 않음. 10Hz 타이머로 줄이면 연산 약 1/3 감소 |
| 주석 이미지를 구독자가 없어도 매 프레임 그림 | 같은 파일 `visualization.draw_detection` 호출부 | 불필요한 CPU |
| 3D LiDAR 720×60 @10Hz (실제 MID-360의 약 2배) | `limbo_description/urdf/limbo.gazebo.xacro` | 브리지·필터·costmap 전체 부하 |
| `person_detector`의 남는 실행기 스레드가 YOLO가 도는 동안 헛돎 (약 20%p) | `person_detector.py` `main()`의 `MultiThreadedExecutor`. 콜백이 한 그룹이라 동시에 못 도는데 다른 스레드가 "실행할 게 있나"를 계속 확인함 | 그냥 싱글스레드로 바꾸면 YOLO 동안 TF를 못 받아 위치 조회가 0.1초씩 기다려 처리량이 절반(14→6.7Hz). TF 대기를 0으로 하면 처리량은 돌아오지만 TF 실패가 0→54번으로 늘어 동작이 바뀜. tf2 `spin_thread=True`는 오히려 CPU 173%. TF만 따로 받는 구조가 필요 |
| MID-360 LiDAR가 설정은 10Hz인데 실제 약 5Hz | `limbo.gazebo.xacro` `update_rate`. 시뮬레이션 시간 기준으로도 5.5Hz이고 간격이 0.1~0.6초로 들쭉날쭉함 (프레임을 건너뜀). 실시간 비율 0.99, GPU 사용률 8%, Gazebo 창을 꺼도(5.5Hz) 켜도(5.4Hz) 같아서 **부하 때문은 아님**. 카메라(15Hz)와 LiDAR(10Hz)를 한 렌더링 루프에서 처리하는 Gazebo 센서 스케줄링 때문으로 추정 | AMCL·costmap 업데이트가 드묾 | LiDAR `update_rate`를 카메라와 맞추거나(5·15Hz) 해상도를 낮춰 다시 측정 |
| 모델 경로가 상대경로 (`yolo11n.pt`) | `person_detector.yaml`의 `yolo.model` | 실행 위치에 따라 모델을 새로 내려받음 |
