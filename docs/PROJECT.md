# limbo 프로젝트 안내

이 저장소를 pull 받아 작업하는 사람과 코딩 에이전트가 **가장 먼저 읽는 문서**다. 무엇을 만드는지, 어떤 전제를 바꾸면 안 되는지, 무엇을 어디에 기록하는지를 정해 두어 작업 방향이 틀어지거나 문서가 난립하지 않게 한다. 최종 갱신: 2026-10-13.

## 1. 무엇을 만드는가

**움직이는 쓰레기통 로봇.** 사람이 많은 실내(학원·서점)와 거리(충장로)를 정해진 경로로 순찰하고, 사람이 다가오면 멈춰서 쓰레기를 받는다. ROS 2 Jazzy + Gazebo Harmonic + Nav2로 시뮬레이션에서 개발하고 실물 v14에 올린다.

- 실물 v14: 차동구동 2륜, 본체 0.50 × 0.59 m, 높이 0.95 m. 모터 IG-32GM(1:71, 정격 83 RPM) × 2, 바퀴 지름 15 cm → **정격 0.65 m/s, 실주행 최고 약 0.8 m/s**. 드라이버 RoboClaw 2x15A
- 센서: Livox MID-360(3D LiDAR + IMU, 지붕), RGB-D 카메라(전방, FOV 72°, 카메라가 낮아 사람은 다리 위주로 보임)
- 소프트웨어: AMCL 위치 추정, NavFn 경로 계획, MPPI 경로 추종, STVL costmap, 사람 예측 경로에 비용을 주는 `human_layer`, YOLO 사람 인식(`person_detector`), waypoint 순찰(`limbo_patrol`), 관제 화면(`dashboard` + `relay_prog` Bridge)

## 2. 바꾸면 안 되는 설계 전제

바꾸려면 팀 합의가 먼저다. 코드나 설정을 고치기 전에 여기와 어긋나지 않는지 본다.

1. **다가오는 사람은 장애물이 아니라 손님이다.** 멈춰서 기다리는 시간은 실패가 아니라 서비스다. 사람을 전부 피하도록 주행을 짜면 안 된다. 사람은 둘로 나눈다: **지나가는 사람**(옆으로 스침·가로지름)에게는 길을 비켜 주고, **다가오는 사람**(속도가 로봇을 향하고 거리가 줄어듦)에게는 피하지 말고 멈춰 기다린다. 그 순간 둘을 완벽히 구분할 수 없으니 애매하면 멈추는 쪽으로 (손님을 피하는 오류가 더 나쁘다).
2. **막혔을 때의 기본 행동은 "기다리기"다.** 사람 틈에서 제자리 회전·후진 같은 복구는 위험하고 이상해 보인다. 사람 때문에 막힌 것과 진짜 막힌 것을 구분해서, 전자는 기다리고 후자만 복구한다. 이 구분은 timeout 숫자 하나가 아니라 behavior tree 분기로 만든다.
3. **후진은 쓰지 않는다.** 후방을 보는 센서가 없다. MID-360은 수직 하향각이 -7°라 가까운 낮은 물체를 못 본다.
4. **속도 상한은 하드웨어 안에서.** Nav2 `vx_max` 0.6 m/s(평지 직진 0.7까지 검토 가능). 4~5 km/h는 구동부 교체 없이는 불가능하고, 팀 회의(2026-10-13)에서 "너무 빠르다"로 결론.
5. **평가는 사람이 움직이는 환경에서 한다.** 사람 없이 알고리즘을 비교하는 것은 의미가 없다. 단 시뮬레이션 사람(actor)은 충돌이 없고 비켜 주지 않으므로, **사람 최소 거리 0.3 m 미만인 "성공"은 충돌로 센다.**
6. **사람 인식은 ID에 기대지 않는다.** 다리만 보여 추적 ID가 자주 바뀐다(하반신 모델 개발 중). 판단은 위치·거리 변화율로 한다.

## 3. 브랜치와 코드 흐름

| 브랜치 | 역할 | 규칙 |
|---|---|---|
| `dev` | 팀 기준. 항상 동작하는 상태 | 원작자(david)와 팀원이 PR로 합침 |
| `ktj` | 주행·관제 통합 작업 | dev를 받아 작업, 안정된 것만 dev로 |
| `lab` | 실험실. 설정·알고리즘 실험 | **실험 코드와 기록은 lab에만 존재한다.** 채택한 변경만 학원 PC가 ktj로 파일 단위로 옮긴다. lab에서는 `git push origin lab`만, dev·ktj에 push 금지, force push 금지 |
| 개인 브랜치 | 각자 작업 | dev에 PR |

흐름은 `dev → ktj → lab`으로 받고, 채택된 것만 `lab → ktj → dev`로 올린다. lab 전용(올리지 않는 것): `tools/sim_trials/`, `experiments/`, 충장로·레이싱 트랙 월드와 생성기, `moving_obstacles.py`, `docs/lab/`, 루트 `CLAUDE.md`.

## 4. 무엇을 어디에 쓰나

문서는 아래 여섯 곳뿐이다. **새 `.md` 파일을 만들지 않는다.** 쓸 곳이 없으면 이 표를 고치는 게 먼저다.

| 곳 | 무엇 | 언제 |
|---|---|---|
| `README.md` | 따라 하면 무엇이 뜨는지. 명령 + 한 줄 결과. 상세는 "자세히" 절 | 실행 방법이 바뀔 때 |
| `docs/CHANGELOG.md` | 커밋을 상세히 쓴 것. 맨 위에 "할 일 / 변경 / 확인" | **push할 때마다** |
| `docs/KNOWN_ISSUES.md` | 아직 못 고친 문제 표 (문제·근거·영향·대책 후보) | 문제를 찾았을 때. 고치면 지우고 TROUBLESHOOTING으로 |
| `docs/TROUBLESHOOTING.md` | 해결한 문제: 증상 → 원인 → 해결 → 확인 | 문제를 고쳤을 때 |
| `experiments/날짜_주제/` (lab) | 실험 조건·결과·결론 README + 그 실험의 CSV·스크립트 | 실험 하나가 끝났을 때 |
| `docs/lab/requests.md`·`reports.md` (lab) | 두 PC 소통. requests는 노트북만, reports는 서브 PC만 쓴다 | 상대 PC에 전할 때 |

설계 문서(`docs/CONTROL_SCREEN.md` 같은 것)는 관제처럼 큰 기능을 **만들기 전에** 쓰는 예외이고, 그 기능 하나당 하나다.

쓰지 않는 것:
- **단순 실수와 무효가 된 실험은 기록하지 않는다.** 좌표를 잘못 찍어 날린 실험, 도구 버그로 무효가 된 회차는 폴더·CSV·변경 기록을 남기지 않고, 이미 올렸으면 정리 커밋으로 지운다. "정정" 항목 대신 유효한 사실만 적는다.
- 변경 기록에 실험 결과표를 통째로 넣지 않는다. 결론 한 줄과 `experiments/` 링크만.
- 큰 파일(메시, rosbag, 지도 PNG 수백 KB 이상)은 커밋하지 않는다. 생성기와 입력 자료만 두고 필요할 때 만든다. 원본 데이터는 `~/limbo_bags/`.
- 코드에 "lab에서 실험했다" 같은 출처 표시를 남기지 않는다. 나중에 dev에 합칠 때 하나의 기록으로 읽혀야 한다.

## 5. 코드 원칙

팀원은 초보자다. 목표는 "파이썬만 알면 읽히는 코드"이지 "깔끔한 코드"가 아니다.

1. 노드 하나 = 일 하나. 노드 이름으로 설명이 안 되면 둘이다.
2. 함수 하나 = 단계 하나, 50줄 이하. 콜백은 단계를 순서대로 부르기만 한다.
3. 계산 로직은 rclpy를 import하지 않는 파일에 두고 pytest로 시험한다.
4. 튜닝 값은 `declare_parameter` + yaml. 코드의 기본값은 yaml 없이도 뜨게 하는 보험이고 한 번 정하면 손대지 않는다. "빌드 없이 바꾸고 싶은 값인가"가 yaml로 갈지의 기준.
5. 디자인 패턴(상속·전략 등)은 실제 대안이 둘 이상 생기기 전에는 쓰지 않는다.
6. 리팩터링은 동작을 바꾸지 않는다. 구조 커밋과 기능 커밋을 나누고, 전후 토픽 출력을 비교한다.
7. 커밋 메시지는 바꾼 이유 한 줄. "수정본", "최종"은 금지.
8. 주석은 "왜"만. 구분선 주석(`# ===== X =====`) 대신 함수로 뽑는다.

왜 그렇게 했는지(숫자의 근거, 포기한 대안)는 docstring·변경 기록·실험 기록 중 한 곳에 남긴다. 예: "5 cm 격자는 1억 칸이 넘어 10 cm로".

## 6. 작업 습관 (에이전트 포함)

- 답변·문서·주석은 한국어. 코드·경로·명령만 원문.
- 프로세스는 PID나 `tools/sim_trials/sim_ctl.sh stop`으로 끈다. `pkill -f`·`pgrep -f` 패턴은 자기 셸까지 죽인다.
- 실험은 `tools/sim_trials/`(README 참고)로 돌린다. 시작 실패는 도구가 3번까지 재시도한다. 한 세트가 한 시간을 넘기면 조건당 1회·구간 2개·제한 60초로 먼저 선별하고, 서브 PC에 나눈다.
- **목표 좌표를 둘 때는 지도 거리 변환으로 벽까지 거리를 확인한다** (inflation 0.45 m 안이면 닿을 수 없다). 열 하나만 훑어 "빈 칸"이라고 믿지 않는다.
- 시뮬레이션 결과를 해석할 때: 실시간 비율(RTF)이 1 아래면 화면이 느려 보이는 것이지 로봇이 느린 게 아니다. 사람 모델은 뚫고 지나갈 수 있다. 바퀴 odom은 제자리 회전에서 9 % 과대다.
- 병합 커밋을 만든 직후에는 `git pull --rebase`를 쓰지 않는다 (병합이 평탄화되어 상대 커밋이 재생된다). `git fetch` 후 원격에 새 커밋이 없으면 바로 push.
- 다른 사람 파일(`docs/lab/reports.md`, 상대 PC의 실험 폴더)은 읽기만 한다.

## 7. 지금 상태 (2026-10-13)

되는 것:
- 학원 2층(`aischool_2f`, 가구 월드 포함) 순찰 완주, 시연 한 줄 실행(`tools/demo_patrol.sh`), 관제 화면에서 일시정지·재개.
- 충장로 200 m·번화가 전체 월드(OSM에서 생성), 왕복 200 m 주행.
- 측정: `nav_recorder`(Goal마다 CSV), `tools/sim_trials/`(반복 시험·속도 단계·bag 분석).
- 확인된 사실: MPPI `prune_distance` 1.7 → 2.5면 0.42 → 0.58 m/s(학원·충장로 둘 다, 안전 지표 변화 없음) — dev 반영 후보. 물리 스텝 2 ms로 RTF 0.6 → 0.95, 정확도 차이 없음.

안 되는 것 (자세한 건 KNOWN_ISSUES):
- 폭 1.8 m 복도에서 두 사람이 나란히 오면 못 지나간다(물리적으로 불가). 한 명이면 지나간다. 로봇이 사람 안으로 들어가는 "성공"이 나온다.
- 시뮬레이션 사람이 비켜 주지 않아 "사람 옆 통과" 실험이 현실과 다르다.

다음 (우선순위):
1. `nav_recorder`에 "사람 0.3 m 미만 = 충돌" 열과 "사람 때문에 멈춘 시간 / 막혀 낭비한 시간" 분리.
2. `human_layer`: 사람 몸 반경 안을 치명 비용으로 (뚫는 궤적 금지). 상수(반경·가우시안 폭·peak)를 yaml로.
3. behavior tree에 "사람이 앞에 있으면 복구 대신 기다리기" 분기 (전제 1·2).
4. 소셜 포스 사람: `moving_obstacles.py` 확장, 유형 셋(비켜 줌·안 비켜 줌·다가와서 멈췄다 감). HuNavSim은 Jazzy/Harmonic 미지원이라 쓰지 않는다. 애니메이션이 필요하면 gz-sim `FollowActor` 플러그인을 본떠 C++로.
5. 그 뒤 속도 설정(0.6 vs 0.75)을 사람 있는 조건에서 재비교. 경로 계획기 비교(NavFn·Smac·Theta*)는 그다음.

하반신 YOLO 모델(`feat/human-leg`)은 팀원이 만드는 중이다. 완성을 기다리지 않고 위 작업을 지금 모델로 진행하고, 오면 `person_model:=`로 바꿔 같은 실험을 다시 돌린다.

## 8. 알려진 제약

- 예측 대상은 전방의 사람뿐이다. RGB-D 시야(72°) 밖의 사람은 LiDAR가 장애물로만 잡는다. 뒤에서 다가오는 손님은 못 본다 (라이다 다리 검출이 보완 후보).
- 낮은 물체는 가까울수록 안 보인다. 0.3 m 높이 물체는 3.5 m 이내, 바닥은 5.9 m 이내가 MID-360 사각. 전방은 RGB-D가 보완.
- 바퀴 odom은 제자리 회전에서 약 9 % 과대(실린더 바퀴 옆미끄러짐). EKF(IMU)와 AMCL이 보정하므로 주행엔 무해.
- RAM 8 GB에서 병렬 빌드하면 멈춘다: `MAKEFLAGS="-j2" python -m colcon build --symlink-install --executor sequential`.
