# limbo 프로젝트 안내

이 저장소를 pull 받아 작업하는 사람과 코딩 에이전트가 **가장 먼저 읽는 문서**다. 팀 전원이 코딩 에이전트와 함께 작업하므로, 이 문서는 사실상 **에이전트에게 주는 전달 사항**이다. 무엇을 만드는지, 어떤 전제를 바꾸면 안 되는지, 무엇을 어디에 기록하는지, 어떤 순서로 일하는지를 정해 두어 작업 방향이 틀어지거나 문서가 난립하지 않게 한다.

최종 갱신: 2026-10-13. 이 문서와 현실이 어긋나면 **이 문서를 먼저 고친다.** 문서를 두고 코드만 바꾸면 다음 사람이 옛 전제로 일한다.

---

## 1. 무엇을 만드는가

**움직이는 쓰레기통 로봇.** 사람이 많은 실내(학원·서점)와 거리(충장로)를 정해진 경로로 순찰하고, 사람이 다가오면 멈춰서 쓰레기를 받는다. "사람을 피해서 목적지에 가는 로봇"이 아니라 **"사람이 쓰려고 다가오는 로봇"**이라는 점이 모든 설계의 출발점이다.

ROS 2 Jazzy + Gazebo Harmonic + Nav2로 시뮬레이션에서 개발하고, 실물 로봇 v14에 올린다.

## 2. 바꾸면 안 되는 설계 전제

여기 있는 것은 실험 결과가 아니라 **팀이 정한 것**이다. 바꾸려면 팀 합의가 먼저이고, 합의되면 이 절을 고친다. 코드·설정·실험을 손대기 전에 아래와 어긋나지 않는지 본다.

### 2-1. 다가오는 사람은 장애물이 아니라 손님이다

- **왜**: 쓰레기통 로봇의 용도가 사람이 다가와 쓰는 것이다. 신기해서 다가오는 사람도 있다. 사람을 전부 피하도록 주행을 짜면 손님을 피해 도망가는 로봇이 된다.
- **실제로는**: 사람을 둘로 나눈다.
  - **지나가는 사람**(복도에서 옆으로 스치거나 가로지름): 길을 비켜 주고 계속 간다. 지금 HumanLayer 방식.
  - **다가오는 사람**(속도 방향이 로봇을 향하고 거리가 줄어듦): 피하지 말고 **제자리에 멈춰 기다린다.** 상호작용(쓰레기 버리기, 구경)이 끝나 멀어지면 다시 출발한다.
- **둘을 구분하는 규칙**(그 순간에는 완벽히 구분 안 됨): ① 사람 속도 방향으로 직선을 그어 로봇 옆을 얼마나 떨어져 지나가는지(최근접점) 본다. 0.6 m 안이면 일단 감속·정지. ② 그 뒤 사람이 1.5 m 안에서 느려지거나 1 m 안에서 1초 이상 멈추면 "다가옴"으로 확정해 기다린다. 그냥 지나가면 재개. **애매하면 멈추는 쪽**으로 기운다. 지나가는 사람에게 멈추는 건 몇 초 손해지만, 손님을 피하는 건 용도 자체를 어기는 것이기 때문이다.
- **하지 말 것**: 사람 예측 경로를 전부 높은 비용으로 칠해 로봇이 사람을 보면 무조건 우회하게 만드는 것. "사람 0.5 m 안에 머문 시간"을 무조건 나쁜 지표로 해석하는 것(손님 응대 시간일 수 있다).

### 2-2. 막혔을 때 기본 행동은 "기다리기"다

- **왜**: Nav2 기본은 10초 동안 0.5 m를 못 가면 경로를 버리고 복구(제자리 회전·후진)로 넘어간다. 사람 틈에서 로봇이 갑자기 돌거나 뒤로 빠지면 위험하고 이상해 보이며, 손님이 쓰레기를 버리는 중에 그러면 안 된다.
- **실제로는**: "사람 때문에 막힘"과 "진짜 막힘(상자·벽)"을 구분해, 앞의 것은 기다리고(상한 수십 초, 상한이 지나면 우회) 뒤의 것만 지금처럼 재계획·복구한다. 구분은 `person_detector`가 내는 사람 위치로 behavior tree 조건 노드에서 한다.
- **하지 말 것**: `progress_checker.movement_time_allowance` 같은 timeout 숫자 하나를 키워서 해결하는 것. 숫자는 사람과 상자를 구분하지 못해 상자 앞에서도 30초를 허비한다. 숫자 조정은 **가설 확인용 진단**으로만 쓰고 채택하지 않는다.

### 2-3. 후진은 쓰지 않는다

- **왜**: 후방을 보는 센서가 없다. MID-360은 수직 하향각 -7°라 가까운 낮은 물체를 못 보고, 카메라는 전방뿐이다.
- **실제로는**: 막혔을 때 탈출 수단은 제자리 회전과 기다리기다. Nav2 `behavior_plugins`에 `backup`이 아직 남아 있는데(시간만 소모) 제거는 할 일 목록에 있다.

### 2-4. 속도 상한은 하드웨어 안에서 둔다

- **왜**: 정격 0.65 m/s, 실주행 최고 0.8 m/s(평지 직진, 가벼운 부하일 때만). 그 이상을 명령하면 모터가 못 따라가 명령과 실제가 어긋나고 odometry 오차만 커진다. 팀 회의(2026-10-13)에서 4~5 km/h는 너무 빠르다고 결론, 구동부 교체 안 함.
- **실제로는**: Nav2 `vx_max` 0.6(평지 직진은 0.7까지 검토 가능), 속도 평활기 `max_velocity`와 Gazebo 구동 플러그인 상한도 같은 값. MPPI가 실제로 내는 속도는 `prune_distance`(최고 속도 × 예측 시간 4초 이상이어야 함)에 좌우된다. 1.7이면 0.42 m/s에 머물고 2.5면 0.58 m/s가 나온다(학원 복도·충장로 둘 다 확인).
- **하지 말 것**: 시뮬레이션에서만 `vx_max`를 1.0 이상으로 올려 "빨라졌다"고 하는 것.

### 2-5. 평가는 사람이 움직이는 환경에서 하고, 시뮬레이션의 한계를 안다

- **왜**: 사람 없이 알고리즘을 비교하면 의미가 없다. 그런데 Gazebo의 사람(actor)은 **충돌이 없어 로봇을 뚫고 지나가고, 절대 비켜 주지 않는다.** 그래서 두 가지 왜곡이 생긴다: 로봇이 사람을 뚫고 "성공"하는 것, 사람이 안 비켜서 영영 못 지나가는 것.
- **실제로는**:
  - 결과 CSV에서 **사람 최소 거리 0.3 m 미만인 "성공"은 충돌로 센다**(사람 모델 반지름 약 0.25 m). 이전 로봇의 "12/12 성공" 중 일부가 이것이었다.
  - 폭 1.8 m 복도에서 두 사람이 나란히 오는 시나리오는 어떤 로봇도 물리적으로 못 지나간다. 이건 "통과" 시험이 아니라 "기다리기" 시험이다.
  - 사람이 비켜 주는 상황은 소셜 포스 모델 사람을 직접 만들어야 시험할 수 있다(할 일 4번). 그때 유형을 셋 둔다: 비켜 주는 사람, 안 비켜 주는 사람(스마트폰 보는 사람), 다가와서 멈췄다 가는 사람(손님).
  - 화면이 느려 보이면 로봇이 느린 게 아니라 실시간 비율(RTF)이 낮은 것이다. 물리 스텝 2 ms로 RTF 0.95를 맞춰 두었다.

### 2-6. 사람 인식은 추적 ID에 기대지 않는다

- **왜**: 카메라가 낮아 다리만 보이고, YOLO 박스가 불안정해 BoT-SORT ID가 자주 바뀐다(한 회차에 수백 번 재연결). 하반신 전용 모델(`feat/human-leg`)을 팀원이 만드는 중이지만 완성을 기다리지 않는다.
- **실제로는**: "다가옴" 판단은 같은 ID의 위치 변화가 아니라, 로봇 앞 2 m 안 사람 점들의 거리 변화율을 0.5초 창으로 본다. ID가 바뀌어도 판단이 이어진다. 라이다 2D 스캔의 다리 검출은 뒤쪽 사각을 메우는 보조 후보다.
- 하반신 모델이 오면 `person_model:=경로`로 바꿔 끼우고 같은 실험을 다시 돌려 ID 바뀜 횟수를 비교한다(`tools/sim_trials/pred_record.py` + `pred_compare.py`).

## 3. 브랜치와 코드 흐름

| 브랜치 | 역할 | 규칙 |
|---|---|---|
| `dev` | 팀 기준. 항상 동작하는 상태 | 원작자(david)와 팀원이 PR로 합친다. 기본 브랜치 |
| `ktj` | 주행·관제 통합 작업 | dev를 받아 작업하고, 안정된 것만 dev로 올린다 |
| `lab` | 실험실 | **실험 코드와 기록은 lab에만 존재한다.** 채택한 변경만 학원 PC가 ktj로 **파일 단위**로 옮긴다. lab에서는 `git push origin lab`만 하고 dev·ktj에 push하지 않는다. force push 금지 |
| 개인 브랜치 (`kkh`, `itkwon`, `sgh`, `bgj`, `feat/human-leg`) | 각자 작업 | dev에 PR |

받는 방향 `dev → ktj → lab`, 올리는 방향 `lab → ktj → dev`(채택된 것만). ktj를 lab에 합칠 때는 병합 커밋을 쓰고, 병합 직후 `git pull --rebase`를 치지 않는다(병합이 평탄화돼 상대 커밋이 재생되며 충돌한다). `git fetch` 후 원격에 새 커밋이 없으면 바로 push.

**lab에만 두고 올리지 않는 것**: `tools/sim_trials/`, `experiments/`, 충장로·레이싱 트랙 월드와 생성기, `scripts/moving_obstacles.py`와 그 launch 연결, `docs/lab/`, 루트 `CLAUDE.md`. 이 목록에 없는 것(설정값, 월드 물리 스텝, 시연 스크립트, waypoint 파일, 문서)은 채택되면 올라간다.

**lab과 dev는 별개로 관리한다.** lab 설정이 dev와 다르더라도 dev에 맞추지 않는다. 다만 ktj가 lab 파일을 통째로 가져오면 dev에서 온 설정이 빠질 수 있으니, 가져올 때 `git diff origin/dev -- 그 파일`로 확인한다.

## 4. 무엇을 어디에 쓰나

문서는 아래 여섯 곳뿐이다. **새 `.md` 파일을 만들지 않는다.** 쓸 곳이 없으면 이 표를 고치는 게 먼저다. 설계 문서(`docs/CONTROL_SCREEN.md` 같은 것)는 관제처럼 큰 기능을 만들기 **전에** 쓰는 예외이고, 기능 하나당 하나다.

| 곳 | 무엇 | 언제 | 양식 |
|---|---|---|---|
| `README.md` | 따라 하면 무엇이 뜨는지 | 실행 방법이 바뀔 때 | 명령 블록 + "→ 그러면 무엇이 열린다" 한 줄. 상세는 맨 아래 "자세히" 절 |
| `docs/CHANGELOG.md` | 커밋을 상세히 쓴 것 | **push할 때마다** 맨 위에 | 아래 양식 |
| `docs/KNOWN_ISSUES.md` | 아직 못 고친 문제 | 문제를 찾았을 때. 고치면 지우고 TROUBLESHOOTING으로 | 표 한 행: 문제 · 근거(언제 어디서 몇 번) · 영향 · 대책 후보 |
| `docs/TROUBLESHOOTING.md` | 해결한 문제 | 고쳤을 때 | `### 증상 — 날짜` 아래 원인 → 해결 → 확인 |
| `experiments/날짜_주제/` (lab) | 실험 하나의 조건·결과·결론 | 실험이 끝났을 때 | `README.md`(왜 했나 / 조건 / 결과 표 / 결론 / 다음) + 그 실험의 CSV·스크립트. 여러 실험이 다시 쓰는 도구는 `tools/sim_trials/`로 |
| `docs/lab/requests.md`, `reports.md` (lab) | 두 PC 소통 | 상대 PC에 전할 때 | requests는 노트북만, reports는 서브 PC만 쓴다. 상대 파일은 읽기만. 긴 지시는 `experiments/orders/` |

### 변경 기록 항목 양식

```
## 2026-10-13 (번호) 한 줄 제목 (무엇을 왜)

**할 일**
- pull 받은 사람이 해야 하는 것. 없으면 "없음". 빌드가 필요하면 `build_limbo`라고 쓴다

**변경**
- 파일: 무엇을 어떻게 바꿨고 **왜** (근거 숫자나 실험 링크)

**확인**
- 어떻게 확인했나 (어느 월드에서 무엇을 돌려 무엇을 봤다)
```

번호는 pull 받은 뒤 맨 위 번호 + 1. 한 항목은 20줄 안쪽. 실험 결과표는 `experiments/` 링크로 대신한다.

### 쓰지 않는 것

- **단순 실수와 무효가 된 실험은 기록하지 않는다.** 목표 좌표를 잘못 찍어 날린 실험, 도구 버그로 무효가 된 회차는 폴더·CSV·변경 기록 항목을 남기지 않는다. 이미 push했으면 정리 커밋으로 지운다(force push 대신 삭제 커밋). "정정" 항목 대신 유효한 사실만 적는다. 실수에서 배운 도구 교훈은 코드 주석(왜)에 남긴다.
- 변경 기록에 실험 결과표·수십 개 숫자를 넣지 않는다. 결론 한 줄과 링크.
- 큰 파일을 커밋하지 않는다: 건물 메시(.obj), rosbag, 수백 KB 지도 PNG, 모델 가중치. 생성기와 입력 자료만 두고 필요할 때 만든다(README "생성해서 쓰는 월드"). 원본 데이터는 `~/limbo_bags/`.
- 코드와 문서에 "lab에서 실험했다" 같은 출처 표시를 남기지 않는다. 나중에 dev에 합칠 때 하나의 기록으로 읽혀야 한다.

### 부작용과 임시 조치는 반드시 두 곳에 적는다

- 무엇을 고치면서 **대가**(부작용)를 받아들이거나, **임시로** 끄거나 값을 크게 둔 것은 `KNOWN_ISSUES.md` 행 **그리고** 이 문서 8절 "다음"에 같이 적는다. 한 곳에만 적으면 묻힌다. 2026-10-12에 전역 STVL(기억 15초)의 부작용("좁은 복도에서 복구 12번")을 해결 기록의 "대가"와 알려진 문제에만 적고 할 일에 올리지 않아, 10-13에 v14가 복도를 못 지나가는 원인을 처음부터 다시 찾았다.
- 값을 고를 때 후보 둘의 성적이 같으면 **작은 쪽(덜 공격적인 쪽)을 고르고 이유를 적는다.** 10-12에 기억 5초와 15초가 같은 성적이었는데 15초를 택했고 근거가 남지 않았다.
- 실험을 시작하기 전에 `KNOWN_ISSUES.md` 맨 위 "지금 주행을 막는 것"을 읽는다. 거기 있는 원인이 실험 결과를 지배하고 있을 수 있다.
- 변경 기록에 "리팩터링 이후/이전" 같은 큰 구분 외에 줄기(lab/ktj)를 따로 만들지 않는다.

## 5. 코드 원칙

팀원은 초보자다. 목표는 "파이썬만 알면 읽히는 코드"이지 "깔끔한 코드"가 아니다. 리팩터링을 제안할 때 아래 기준에 비춰 설명할 수 있어야 한다.

1. **노드 하나 = 일 하나.** 노드 이름으로 하는 일이 설명 안 되면 둘로 나눌 때다. 반대로 지금 `person_detector`는 인식·추적·예측을 한 노드에 두는데, 나누는 건 인식이 느려지거나 다른 노드가 인식 결과를 따로 써야 할 때다.
2. **함수 하나 = 단계 하나, 50줄 이하.** 콜백은 단계 함수를 순서대로 부르기만 한다. 같은 이유로 함께 바뀌는 로직을 억지로 쪼개지 않는다.
3. **계산 로직은 `rclpy`를 import하지 않는 파일에** 두고 pytest로 시험한다(`limbo_perception/geometry.py`가 예).
4. **튜닝 값은 `declare_parameter` + yaml.** 코드의 기본값은 yaml 없이도 노드가 뜨게 하는 보험이고 한 번 정하면 손대지 않는다. 튜닝은 yaml에서만. "빌드 없이 바꾸고 싶은 값인가"가 yaml로 갈지의 기준이고, 그 외 의미 있는 숫자는 이름 붙은 상수로. 지금 `human_layer.cpp`의 사람 반경·가우시안 폭·peak가 상수로 박혀 있는 건 고칠 대상(할 일 2번).
5. **디자인 패턴(상속·추상 클래스·전략)은 실제 대안이 둘 이상 생기기 전에는 쓰지 않는다.** 같은 if/elif가 세 곳 이상 반복될 때가 기준.
6. **리팩터링은 동작을 바꾸지 않는다.** 구조 커밋과 기능 커밋을 나눈다. 확인은 카메라 입력 rosbag 하나를 녹화해 전후로 재생하고 출력을 허용 오차로 비교한다.
7. **커밋 메시지는 바꾼 이유 한 줄.** "수정본", "최종" 금지. `__pycache__`, `.pyc`, 백업 파일은 `.gitignore`.
8. **주석은 "왜"만.** 무엇을 하는지는 코드가 말한다. 구분선 주석(`# ===== X =====`)을 쓰고 싶으면 그 자리를 함수로 뽑아 이름을 붙인다.

**왜 그렇게 했는지는 반드시 남긴다.** 숫자의 근거("5 cm 격자는 1억 칸이 넘어 10 cm로", "inflation은 로봇 바깥 반지름 0.39보다 커야 MPPI가 외곽 충돌을 제대로 봄"), 포기한 대안(HuNavSim은 Jazzy 미지원), 틀렸던 가설의 결론. 자리는 docstring·yaml 주석·변경 기록·실험 기록 중 그 값을 보는 사람이 가장 먼저 만나는 곳.

## 6. 작업 절차

### 실험을 할 때

1. 질문을 한 문장으로 적는다 ("prune_distance를 올리면 사람 회피를 유지한 채 빨라지는가").
2. 조건을 정한다: 월드, 경로, 반복 횟수, 바꾸는 값 **하나**. 기준(지금 설정)을 반드시 같이 돌린다. 어제 결과와 비교하지 않는다(그 사이 로봇·월드·설정이 바뀌었을 수 있다).
3. **목표 좌표는 지도 거리 변환으로 벽까지 거리를 확인한다.** inflation 0.45 m 안이면 닿을 수 없는 목표다. 지도 열 하나만 훑어 "빈 칸"이라고 믿지 않는다.
4. 선별은 짧게: 조건당 1회, 구간 2개, 제한 60초로 30분 안에 추리고, 최종 후보만 3회씩. 한 세트가 한 시간을 넘기면 서브 PC에 나눈다(`docs/lab/requests.md`).
5. 도구는 `tools/sim_trials/`(그 폴더 README). 시뮬레이션은 `sim_ctl.sh start/stop`으로. 시작 실패는 도구가 3번까지 재시도한다.
6. 결과를 볼 때 확인할 것: 사람 최소 거리 0.3 m 미만은 충돌, 복구 횟수, 실시간 비율, 그리고 **로봇이 실제로 어디서 멈췄는지**(녹화한 정답 위치로). 성공/실패 수만 보고 원인을 단정하지 않는다.
7. 기록은 `experiments/날짜_주제/README.md`에 조건·결과·결론·다음. 변경 기록에는 한 줄과 링크.
8. 무효가 됐으면(좌표 실수, 도구 버그, 좀비 프로세스) 폐기하고 기록하지 않는다. 그 원인이 도구 문제면 도구를 고치고 코드 주석에 왜를 남긴다.

### 설정값을 채택할 때

- 두 곳 이상의 다른 환경(예: 학원 복도와 충장로)에서 같은 방향의 결과가 나와야 "채택 후보"다.
- 채택 후보는 변경 기록에 "dev 반영 후보"로 적고, ktj 반영은 학원 PC에서 한다. lab에서 임의로 ktj·dev를 고치지 않는다.
- 지금 채택 후보: MPPI `prune_distance` 1.7 → 2.5 (0.42 → 0.58 m/s, 안전 지표 변화 없음).

### push 전 점검

- 변경 기록 맨 위에 항목을 추가했는가. 번호는 맨 위 + 1인가.
- 큰 파일이 들어가지 않았는가 (`git diff --cached --stat`).
- lab 전용 파일을 ktj·dev로 보내고 있지 않은가.
- 설정 파일(`nav2_params.yaml`, `limbo.gazebo.xacro`)이 실험 중 값으로 남아 있지 않은가 (`git diff`).
- 해결한 문제가 KNOWN_ISSUES에 남아 있지 않은가.

### 에이전트 작업 습관

- 답변·문서·주석은 한국어. 코드·경로·명령만 원문.
- 프로세스는 PID나 `sim_ctl.sh stop`으로 끈다. `pkill -f`·`pgrep -f` 패턴은 자기 셸까지 죽인다. 백그라운드 `ros2 bag record`는 `kill -INT`로 안 멈추고 `kill -TERM`이어야 한다.
- 시뮬레이션은 한 번에 하나만 띄운다. 끝나면 `ps`로 `gz sim`과 launch가 남지 않았는지 본다. 남은 노드가 겹치면 다음 회차의 Nav2 시작까지 실패한다.
- Nav2가 "준비됨"이어도 `bt_navigator`가 active가 아니면 목표가 영영 처리되지 않는다. 도구는 이를 확인하지만 손으로 띄울 때는 `ros2 lifecycle get /bt_navigator`로 본다.
- 다른 사람 파일(`docs/lab/reports.md`, 상대 PC의 실험 폴더)은 읽기만 한다.
- 사용자가 결정해야 하는 것(설계 전제 변경, 하드웨어, dev 반영)은 임의로 하지 않고 근거와 선택지를 정리해 묻는다. 그 외 되돌릴 수 있는 일은 묻지 않고 한다.

- `backup` 복구 제거(전제 2-3). MID-360 기울기 각도(기울이면 `pointcloud_to_laserscan` 프레임과 STVL `vertical_fov_offset`을 같이 고쳐야 함). 하반신 모델이 오면 ID 바뀜 비교.
- 헛돎 감시의 주행 취소가 **임시로 꺼진 상태**(10-12, 팀원 환경 오탐). 진짜 막혔을 때 상자를 2분 동안 밀었던 적이 있어, 오탐 원인을 잡은 뒤 취소를 다시 켜거나 "정지·경고"로 바꿀지 정해야 한다.
- Nav2가 목표를 한 번 실패하면 순찰 노드가 순찰 전체를 끝낸다(일시정지 뒤 재개해도 못 이어 감). 몇 번 재시도 후 다음 waypoint로 넘어가는 처리.
- 센서 배치(카메라 높이·각도, LiDAR 기울기)와 하반신 모델을 기본으로 쓸지는 실물을 보고 결정. `person_detector` 코드 개선(YOLO를 10 Hz 타이머로, 주석 이미지는 구독자 있을 때만, 남는 실행기 스레드, 모델 절대 경로)은 KNOWN_ISSUES "코드" 절.

## 9. 알려진 제약

- 예측 대상은 전방의 사람뿐이다. RGB-D 시야(72°) 밖의 사람은 LiDAR가 장애물로만 잡아 반응적으로만 피한다. 뒤에서 다가오는 손님은 못 본다(라이다 다리 검출이 보완 후보).
- 낮은 물체는 가까울수록 안 보인다. 0.3 m 높이는 3.5 m 안, 바닥은 5.9 m 안이 MID-360 사각. 전방은 RGB-D가 보완.
- 바퀴 odom은 제자리 회전에서 약 9 % 과대(실린더 바퀴 옆미끄러짐). EKF(IMU)와 AMCL이 보정하므로 주행엔 무해하지만 odom만 믿는 판단은 금물.
- Gazebo actor는 충돌이 없고 대본대로만 걷는다(2-5).
- RAM 8 GB에서 병렬 빌드하면 멈춘다: `MAKEFLAGS="-j2" python -m colcon build --symlink-install --executor sequential`.
- Nav2 시작 때 `collision_monitor`의 lifecycle 응답이 끊겨 configure 단계에서 멈추는 일이 가끔 있다. 시험 도구는 `bt_navigator` active를 확인하고 다시 띄운다.
