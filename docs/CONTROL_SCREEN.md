# 관제 화면 설계 (사용자용)

작성: 2026-10-12 (ktj) · 상태: **A-1단계(순찰 노드) 구현·시험 완료**, 나머지는 설계

관제 화면은 사실상 **사용자(관리자)가 보는 화면**이다. 사용자가 할 일은 "지금 로봇이 어디서 무엇을 보고 있는지 보고, 필요하면 멈추고 다시 보내는 것"뿐이라 기능을 그만큼으로 줄인다.
대시보드·Bridge는 itkwon에게서 넘겨받아 ktj가 마무리한다 (2026-10-13). 범위가 바뀌는 부분은 구현하면서 PRD(`dashboard/docs/PRD.md`, `relay_prog/docs/PRD.md`)에 반영한다 (아래 "PRD와 달라지는 것").

## 화면 구성

| 영역 | 내용 | 설계 |
|---|---|---|
| 버튼 | **일시정지**, **순찰 재개** 2개 | [A](#a-일시정지순찰-재개) |
| 지도 | SLAM 지도 위에 로봇 위치·방향, 순찰 경로, 다음 목표 | [B](#b-지도와-로봇-위치) |
| 카메라 | 전방 카메라 실시간 화면 (볼 때만) | [C](#c-카메라-화면) |
| 상태 요약 | 연결·센서를 "정상 / 확인 필요" 한 줄로. 자세한 표는 접어 둠 | [D](#d-상태-요약) |
| 알림 | 지금 그대로 (최근 100건) | 변경 없음 |

### PRD와 달라지는 것

|---|---|

# A. 일시정지·순찰 재개

순찰 중인 로봇을 **정지**하고 그 자리부터 **재개**한다. 대시보드 PRD §5.4 "후속 실제 제어의 필수 조건"을 실제로 구현한다.

## 결정한 것

| 항목 | 결정 | 이유 |
|---|---|---|
| 명령 전달 | ROS2 **서비스** (`std_srvs/srv/Trigger`) | 요청 1번에 "접수 / 거절(사유)" 응답 1번. 토픽은 받았는지 알 수 없어서 PRD의 "명시적 거절"과 "응답 없음"을 구분 못 함 |
| 결과 확인 | 순찰 노드의 **상태 토픽** | 서비스 응답은 "접수했다"까지. 실제로 멈췄는지·다시 움직이는지는 상태로 확인해야 함 (PRD: 클릭·응답만으로 성공 표시 금지) |
| 액션은 쓰지 않음 | — | 액션 goal은 "시작 → 끝"뿐이라 일시정지가 없다. 정지마다 goal이 끝나고 재개마다 새 goal이 생겨, 취소와 재개가 겹치거나 goal 주인이 여럿이면 꼬일 수 있음. 상태는 순찰 노드 하나가 들고 서비스는 그 상태를 바꿔 달라는 요청만 한다 |
| 재전송 | 하지 않음 | 응답이 없으면 "확인 불가"로 끝내고 운영자가 상태를 보고 다시 누른다. 늦게 도착한 정지가 두 번 처리되는 것을 막음 (PRD §5.3) |

**이 정지는 비상정지가 아니다.** 사용자가 급할 때 먼저 누르는 버튼으로 쓸 수 있지만, 네트워크·서버·Bridge·순찰 노드가 모두 살아 있어야 동작하고 멈출 때까지 시간이 걸린다(예상 1~2초, 1단계에서 측정). 하드웨어 비상정지는 하드웨어 파트가 따로 만든다.

## 전체 흐름

```
[관제 화면] 정지 클릭
   → 서버: request_id 발급, 명령 대기열에 넣음 (유효 5초)
   → Bridge: 명령을 받아 /patrol/pause 서비스 호출 (제한 3초)
   → 순찰 노드: 상태 확인 후 접수/거절 응답 → Nav2 주행 취소 → 상태 paused 발행
   → Bridge: 서비스 응답과 순찰 상태를 서버로 보냄
   → 서버: request_id별로 "요청 → 로봇 응답 → 상태 확인" 판정 → 화면 표시
```

| 단계 | 정지 성공 조건 | 재개 성공 조건 |
|---|---|---|
| 로봇 응답 | 서비스 `success: true` | 서비스 `success: true` |
| 상태 확인 | 요청 이후 시각의 순찰 상태 `paused` **그리고** 그 뒤 주행 정보가 정지 기준 미만 | 요청 이후 시각의 순찰 상태 `patrolling` (속도 상승만으로 판정 금지) |
| 실패 | `success: false` (사유 표시) | `success: false` (사유 표시) |
| 확인 불가 | 응답 없음(3초), 상태 확인 없음(5초), 중간 연결 끊김 | 같음 |

## 1단계: 순찰 노드 (`limbo_patrol`)

대시보드 없이 `ros2 service call`로 혼자 시험할 수 있다. 이 단계만 먼저 구현·검증한다.

### 인터페이스

| 이름 | 종류 | 내용 |
|---|---|---|
| `/patrol/pause` | 서비스 `std_srvs/srv/Trigger` | 순찰 중이면 Nav2 주행을 취소하고 멈춤 |
| `/patrol/resume` | 서비스 `std_srvs/srv/Trigger` | 멈춘 곳부터 이어서 순찰 |
| `/patrol/state` | 토픽 `limbo_interfaces/msg/PatrolState` (새로 추가) | 상태가 바뀔 때마다 발행. QoS `reliable` + `transient_local` 깊이 1 (늦게 붙은 구독자도 마지막 상태를 바로 받음) |

`PatrolState` 필드 (안):

| 필드 | 형식 | 뜻 |
|---|---|---|
| `stamp` | `builtin_interfaces/Time` | 상태가 바뀐 시각 (명령 이후 상태인지 판정용) |
| `state` | `string` | `waiting_localization` · `patrolling` · `pausing` · `paused` · `completed` · `failed` |
| `waypoint_index` / `waypoint_count` | `uint32` | 다음 목표 waypoint 번호 / 전체 수 |
| `waypoint_name` | `string` | 다음 목표 이름 (A, B, …) |
| `has_resumable_task` | `bool` | 재개할 수 있는지 (PRD의 재개 허용 판단) |
| `reason` | `string` | 마지막으로 바뀐 이유 (예: `pause requested`, `Navigation failed`) |

### 접수·거절 규칙

| 요청 | 지금 상태 | 응답 |
|---|---|---|
| pause | `patrolling` | 접수 → `pausing` → 취소 확인 후 `paused` |
| pause | `paused`, `pausing` | 거절: `already paused` |
| pause | `completed`, `failed`, `waiting_localization` | 거절: `not patrolling` |
| resume | `paused` | 접수 → `patrolling` |
| resume | `patrolling` | 거절: `already patrolling` |
| resume | 그 밖 | 거절: `nothing to resume` |

### 재개 위치

- 지금은 `pass` waypoint를 모아 `goThroughPoses`로 한 번에 보내고 `stop` waypoint에서 끊는다.
- 정지할 때 Nav2 피드백의 `number_of_poses_remaining`으로 **이번 구간에서 아직 안 지난 waypoint**를 기억한다. 재개는 그 waypoint들만 다시 보낸다 (이미 지난 곳으로 되돌아가지 않음).
- `stop` 지점에서 기다리는 중(`wait_sec`)에 정지하면 남은 대기는 버리고, 재개하면 다음 구간으로 간다.

### 코드 구조 변경

- 지금 `main()`은 `BasicNavigator`로 처음부터 끝까지 도는 한 줄짜리 흐름이고, 밖에서 끼어들 수 없다.
- 서비스와 상태 발행은 **별도 노드**(`patrol_control`)에 두고 백그라운드 스레드에서 spin한다. `BasicNavigator`는 자기 안에서 spin하므로 같은 노드에 서비스를 붙이면 콜백이 막힌다.
- 두 쪽은 잠금으로 보호한 상태 하나와 정지 요청 플래그로만 주고받는다. 서비스 콜백은 상태만 보고 즉시 응답하고, Nav2 취소는 주행 루프가 한다 (응답이 Nav2를 기다리지 않음).
- 지금처럼 Nav2가 다른 이유로 취소·실패하면 `failed`로 끝난다. **우리가 요청한 취소만** `paused`로 본다.
- `waypoints` 파라미터(월드별 파일 선택)는 lab에만 있다. 이 작업과 별개로 두고, 필요하면 따로 dev에 올린다.

### 시험 (시뮬레이션)

```bash
limbo && export ROS_DOMAIN_ID=98 GZ_PARTITION=desk
ros2 run limbo_patrol patrol_node --ros-args -p use_sim_time:=true
ros2 topic echo /patrol/state
ros2 service call /patrol/pause std_srvs/srv/Trigger
ros2 service call /patrol/resume std_srvs/srv/Trigger
```

| 확인 | 기대 |
|---|---|
| 주행 중 pause | 응답 `success: true`, 상태 `pausing` → `paused`, `/cmd_vel` 0, 로봇 정지 |
| pause 두 번 | 두 번째는 `already paused` |
| resume | 상태 `patrolling`, 남은 waypoint부터 주행, 지난 waypoint로 되돌아가지 않음 |
| `stop` 대기 중 pause → resume | 다음 구간으로 진행 |
| 끝까지 | 상태 `completed`, 이후 pause는 `not patrolling` |
| 순찰 노드 없이 서비스 호출 | 호출 쪽 제한 시간 후 실패 (2단계 Bridge의 "응답 없음") |
| **정지까지 걸린 시간** | 서비스 호출 시각 → 정답 위치(`/ground_truth/odom`) 속도가 0.05 m/s 미만이 된 시각. 10번 재서 최대·평균을 기록. 느리면 정지 즉시 속도를 0으로 막는 방법을 검토 |

문제와 고칠 방법 (정해야 함):

| # | 문제 | 원인 | 고칠 방법 (안) |
|---|---|---|---|
| 1 | 화면은 "확인 불가"로 끝났는데 몇 초 뒤 로봇이 실행함. 재개였다면 **로봇이 예고 없이 출발**할 수 있음 | Bridge의 long poll이 이미 열려 있어 서버는 넘겼다고 봄(`delivered`). 유효 시간(`ttl_ms`)을 Bridge가 **실제로 읽은 순간부터** 세서, 전달이 늦으면 늦게 실행됨 | Bridge가 서비스를 부르기 직전 서버에 "아직 유효한가" 확인(`claim`)하고, 그 왕복 시간을 Bridge가 직접 재서 1초를 넘으면 실행하지 않음. 서버는 응답 제한이 지난 명령은 거절 |
| 2 | 순찰 노드가 죽어도 화면은 "순찰 중", 재개 사유가 틀리고, 결과가 "응답 없음"(실제로는 서비스 없음) | 순찰 상태는 마지막 값을 계속 보냄. 서비스 준비 여부를 늦게 알아챔 | Bridge가 `/patrol/state` 발행자가 없으면 순찰 상태를 "확인 불가"로 보냄 → 화면 "순찰 프로그램 꺼짐", 버튼 사유도 맞게 |
| 3 | 재개 직후 한 번의 내비게이션 실패로 순찰 전체가 끝남 | 컨트롤러가 TF 시각 차이(10 ms)로 목표를 포기. 순찰 노드는 실패하면 바로 끝냄 | 순찰 노드가 실패한 구간을 1~2번 다시 시도. 내비게이션 쪽 일이라 별도로 정함 |

# B. 지도와 로봇 위치

지금은 **SLAM 지도**를 쓰고, 나중에 사용자가 보기 쉬운 **약도**로 바꾼다.

## 지도

| 항목 | 값 |
|---|---|
| 원본 | `limbo_navigation/maps/aischool_2f_map.pgm` + `.yaml` (492 × 471 px, 0.05 m/px → 약 24.6 × 23.6 m, 원점 (−12.842, −7.834)) |
| 보내는 방법 | 서버가 시작할 때 pgm을 PNG로 한 번 바꿔 정적 파일로 제공. 해상도·원점도 같이 내려줌. 지도는 주행 중 바뀌지 않으므로 Bridge로 보내지 않음 |
| 지도 고르기 | 서버 설정(`config.json`)에 지도 yaml 경로. 월드를 바꾸면 이 값만 바꿈 |

나중에 약도로 바꿀 때: 약도 그림과 함께 **지도 좌표 → 그림 좌표 변환**(기준점 2~3개로 맞춘 변환값)을 설정에 둔다. 화면은 이 변환만 거쳐 그리므로 위치·경로 표시 코드는 그대로 쓴다.

## 로봇 위치

| 항목 | 값 |
|---|---|
| 원본 | 위치·방향: TF `map → base_footprint` (Bridge가 0.5초마다 읽음). 불확실성: `/amcl_pose` 공분산 |
| 보내는 값 | x, y, 방향(yaw), 위치 불확실성(공분산에서 구한 반경), 받은 시각 |
| 주기 | 1초에 1번 (텔레메트리와 같이). 숫자 몇 개라 가벼움 |
| 화면 | 로봇 아이콘 + 방향 화살표. 불확실성이 크면 원을 크게 그려 "위치가 정확하지 않음"을 보여 줌. 위치가 3초 넘게 안 오면 흐리게 + "위치 확인 불가" |

## 순찰 경로·다음 목표

- waypoint 목록(이름·좌표)은 순찰 노드가 시작할 때 한 번 알려 주고, 다음 목표는 A의 `/patrol/state`(`waypoint_index`)로 표시한다
- 화면: 경로를 점선으로, 지난 waypoint는 흐리게, 다음 목표는 강조

## 정할 것

- ~~위치를 텔레메트리 계약에 넣을지~~ → v2에 넣음
- ~~멈춰 있을 때 위치~~ → **TF로 바꿈** (2026-10-13, CHANGELOG (26)). AMCL은 로봇이 일정 거리·각도(`update_min_d`·`update_min_a`, 설정 파일에 따라 0.1~0.25 m)를 움직일 때만 `/amcl_pose`를 내서, 일시정지·순찰 완료 뒤에는 화면이 "위치 확인 불가"로 흐려졌다. TF는 오도메트리가 계속 나오므로 멈춰 있어도 갱신된다. 다른 후보였던 "화면 판정만 바꾸기(멈춰 있으면 마지막 위치를 믿기)"는 추정이 들어가서, "AMCL 설정 바꾸기"는 Jetson CPU·내비게이션에 영향이 있어서 뺐다

| Jetson | 처음엔 OpenCV JPEG(CPU)로 만들고 CPU 사용률을 잼. 부담되면 Jetson 하드웨어 JPEG 인코더로 바꿈 |
