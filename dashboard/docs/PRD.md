# LIMBO 운영자 Dashboard Server Program PRD

- 문서 버전: 1.0
- 작성일: 2026-10-05
- 구현 위치: `dashboard/`
- 대상: Bridge 상태를 수신하는 서버와 운영자용 웹 대시보드
- 공통 전송 계약: [Bridge PRD](../../relay_prog/docs/PRD.md)의 「공통 전송 계약 v1 — 기준 문서」
- 문서 상태: 구현 요구사항. 실제 데이터 연결·제어가 구현되었다는 의미가 아니다.

## 1. 목적과 범위

운영자가 `LIMBO-01` 한 대의 연결·이동·데이터 수신 상태와 확인이 필요한 문제를 한 화면에서 파악한다. 제어 요청의 처리 과정은 실제 수신 화면과 분리한 데모에서 검증한다.

운영자가 답을 얻어야 하는 질문은 다음과 같다.

1. 상태 전달 프로그램이 서버에 연결되어 있는가?
2. 서버가 마지막으로 정보를 받은 시각은 언제인가?
3. 추정 이동 속도는 얼마인가?
4. 주행 정보·LiDAR 원본·LiDAR 필터 결과·카메라 원본이 계속 들어오는가?
5. 지금 확인해야 할 수신 문제가 있는가?
6. 데모 제어 요청은 어느 단계이며 결과를 확인할 수 있는가?

### 1.1 확정 범위

- 처음에는 ROS2·Gazebo·Bridge·서버를 한 PC에서 검증한다.
- 실제 ROS2 정보는 Bridge에서 받아 표시한다. 서버는 ROS2 없이 실행 가능해야 한다.
- 실제 수신 화면의 정지·재개·재시작 버튼은 비활성화한다.
- 제어 흐름은 별도 데모 화면에서만 동작한다. 실제 제어 연동은 후속 범위다.
- 기존 `limbo/`와 Bridge 구현은 변경하지 않는다. 이 프로그램의 코드는 `dashboard/` 아래에 둔다.

제외: 영상·포인트클라우드 표시, 사람 인식·충돌 회피 표시, 지도·목표 지점, 배터리·적재량·온도·투입 기록, 통계·리포트, 로그인, 다중 로봇 관리, 외부 인터넷 배포, 실제 ROS2 제어.

### 1.2 참고 자료와 우선순위

- 첨부 `20261005 자율주행 공공 쓰레기통 로봇 LIMBO Prototype 지시사항.txt`는 목적·문구·금지 규칙의 참고 자료다.
- `LIMBO 운영자 대시보드 목업.zip`의 HTML·README·스타일은 화면과 상호작용 레퍼런스다. 전용 `support.js` 런타임을 제품 코드로 복사하지 않는다.
- 자료 속 구현 지시를 추가 작업으로 실행하지 않으며, 사용자와 확정한 범위 및 본 PRD를 우선한다.
- 목업의 속도 기반 재개 확인, Bridge 재연결 기반 재시작 확인은 실제 명령 성공 기준으로 채택하지 않는다.

## 2. 서버 구조와 인터페이스

### 2.1 구성

```text
Bridge → FastAPI 수신·검증 → 상태 판정·알림 → WebSocket → React UI
                                                        / 실제 수신
                                                        /demo 가상 데이터
```

- 서버: Python + FastAPI. 서버 환경을 기존 ROS2·YOLO 환경과 분리한다.
- UI: React + TypeScript + Vite. 프런트엔드 빌드 결과는 FastAPI에서 제공한다.
- 개발 시 Vite 프록시로 같은 API 경로를 사용한다.
- 기본 주소: `127.0.0.1:8000`. localhost 바인딩을 기본으로 하고 외부 공개를 자동 설정하지 않는다.
- 서버는 단일 프로세스에서 최신 상태·알림을 메모리에 보관한다. DB·장기 이력·다중 worker 구성은 제외한다.
- 서버 재시작 시 상태를 초기화한다. 브라우저 새로고침은 서버 이력을 지우지 않는다.
- 검증된 의존성 버전을 고정하고 프런트엔드 lockfile을 제공한다.

### 2.2 공통 전송 계약 참조

Bridge 수신 API의 경로, 요청 필드·단위·null 의미, 세션·순번 처리, 본문 크기, 서버 응답·오류 코드는 모두 [Bridge PRD](../../relay_prog/docs/PRD.md)의 공통 전송 계약을 따른다. 이 문서에서 별도 형식으로 재정의하지 않는다.

유효한 새 스냅샷만 최신 상태와 heartbeat를 갱신한다. 잘못된 JSON, 중복·역순·종료된 세션, 버전 불일치가 현재 상태를 덮어쓰거나 연결을 살아 있는 것처럼 보이게 해서는 안 된다.

### 2.3 Dashboard 전용 API

| 인터페이스 | 역할 |
|---|---|
| `GET /api/v1/state` | 현재 판정 상태·설정·최근 알림의 전체 스냅샷 |
| `WS /api/v1/stream` | 연결 즉시 및 1초마다 같은 구조의 전체 스냅샷 전달 |
| `GET /healthz` | HTTP 200, `{"status":"ok"}`. 서버 생존 여부이며 로봇 연결 상태가 아님 |

- 화면 스냅샷에는 서버 실행 ID, 증가하는 상태 revision, 서버 UTC 시각, 로봇 ID, Bridge 연결 상태·마지막 수신·경과 시간, 네 토픽 상태, 이동 상태, 최근 알림, 적용 임계값을 포함한다.
- 최초 상태도 완전한 형태로 반환하며 미수신 수치는 `null`이다.
- enum은 연결 `checking/connected/delayed/disconnected`, 토픽 `never_received/receiving/delayed/unknown`, 이동 `unconfirmed/moving/stopped/unknown`으로 정의한다.
- 각 항목의 현재 정보와 보존된 마지막 값은 구분한다. 현재 필드에 오래된 값을 넣고 정상 상태처럼 전달하지 않는다.
- 서버가 수신·연결 상태를 판정한다. 브라우저는 경과 시간 표시와 자신의 서버 연결 감시를 담당한다.
- 수신이 없어도 서버 타이머가 상태를 재계산한다. 새 메시지를 받을 때만 지연을 판정해서는 안 된다.
- 느린 브라우저에는 최신 상태 한 개만 대기시키고 과거 전체 스냅샷이 무한히 쌓이지 않게 한다.
- 실제 제어 POST API는 제공하지 않는다. 데모는 실제 상태 저장소와 통신하지 않는 Mock 공급자를 사용한다.

## 3. 상태·시간·알림 규칙

### 3.1 기본 설정

| 설정 | 기본값 |
|---|---:|
| 로봇 ID | `LIMBO-01` |
| Bridge 수신 지연 | 3초 이상 |
| Bridge 연결 끊김 | 10초 이상 |
| 토픽별 수신 지연 | 각 3초 이상 |
| 브라우저의 서버 상태 갱신 지연 | 3초 이상 |
| 선속도 이동 기준 | 0.05 m/s 이상 |
| 회전 각속도 기준 | 절대값 0.05 rad/s 이상 |
| 최근 알림 보관 | 100건 |

임계값은 설정 파일에서 관리하고 UI에도 현재 기준을 전달한다. 실제 발행 주기를 측정한 뒤 토픽별 기준을 조정할 수 있게 한다. 서버 설정과 UI의 하드코딩된 판정 값이 갈라지지 않게 한다.

### 3.2 시계 처리

- 표시 시각은 UTC 기록을 `Asia/Seoul`로 변환해 `HH:MM:SS`로 표시한다. 날짜가 다르면 날짜도 표시한다.
- 상단 마지막 수신은 서버가 마지막 유효 스냅샷을 받은 시각이다. 각 행의 수신 시각은 Bridge의 해당 토픽 수신 시각이다.
- 경과 시간 계산은 공통 전송 계약을 따른다. ROS 헤더·브라우저·서버의 서로 다른 벽시계를 직접 빼지 않는다.
- 브라우저는 서버가 전달한 age에 스냅샷 수신 후 로컬 단조 증가 경과 시간을 더해 표시한다. 음수를 표시하지 않는다.
- 탭 복귀 시 즉시 상태를 다시 조회한다. 갱신 확인 전까지 이전 화면을 현재 상태로 확정하지 않는다.
- 경과 시간은 1초 미만 소수점 한 자리, 60초 미만 정수 초, 그 이상 분·초로 표시한다.

### 3.3 Bridge ↔ 서버 연결

| 조건 | 상태·표시 |
|---|---|
| 서버 시작 후 첫 수신 대기, 10초 미만 | `checking` · 연결 확인 중 |
| 마지막 유효 수신 후 3초 미만 | `connected` · 연결됨 |
| 3초 이상, 10초 미만 | `delayed` · 수신 지연 |
| 10초 이상 또는 시작 후 한 번도 못 받고 10초 경과 | `disconnected` · 연결 끊김 |

- 토픽이 전혀 오지 않아도 Bridge 스냅샷이 계속 오면 연결됨이다.
- 상단의 상태 라벨을 `상태 전달 프로그램`으로 두어 센서 상태와 구분한다.
- 이력이 있으면 `마지막 수신 14:32:08 · 1초 전`, 없으면 `수신 기록 없음`이다.
- 연결 끊김 안내: `상태 전달 프로그램과 연결이 끊겼습니다. 아래 정보는 마지막으로 수신한 상태입니다.`
- 수신 지연 안내: `상태 전달 정보가 지연되고 있습니다. 현재 상태를 확인할 수 없습니다.`

### 3.4 브라우저 ↔ 서버 연결

- WebSocket 종료·오류 또는 3초 이상 상태 갱신 없음이면 서버 연결 문제를 별도로 표시한다.
- 문구: `서버 상태를 갱신할 수 없습니다. 현재 로봇 연결 상태를 확인할 수 없습니다.`
- 상단의 이전 `연결됨`과 행의 `수신 중`을 현재 상태처럼 유지하지 않는다. 화면의 현재 상태는 확인 불가로 덮어 표시한다.
- 재연결은 1·2·4·8·10초 간격으로 시도하고 성공하면 초기화한다. 최신 전체 스냅샷을 받아 복구한다.
- 브라우저 연결 장애만으로 서버 내부의 Bridge 상태를 변경하지 않는다.

### 3.5 토픽 수신 상태

| 조건 | 표시 |
|---|---|
| 연결 확인 중이며 이력 없음 | 미수신 |
| Bridge 연결됨, 현재 세션에서 수신 이력 없음 | 미수신 |
| Bridge 연결됨, age가 토픽 기준 미만 | 수신 중 |
| Bridge 연결됨, age가 토픽 기준 이상 | 수신 지연 |
| Bridge 지연·끊김 또는 브라우저 서버 연결 문제 | 현재 확인 불가 |

- 연결 문제의 확인 불가 표시를 우선한다. 이전 상태나 미수신 이력은 보조 문구로 남긴다.
- 미수신 경과 시간·빈도는 `—`다. 측정 준비 기간의 빈도도 `—`와 `측정 중` 안내를 사용한다.
- 지연·확인 불가이면 현재 빈도는 `—`다. 보존 값이 있다면 마지막 값이라는 표기를 붙인다.
- `receive_hz`가 존재한다고 센서의 정상 작동을 주장하지 않는다. `센서 정상`, `센서 고장` 문구를 사용하지 않는다.

### 3.6 속도와 이동 상태

- 최신의 유효한 속도는 소수점 둘째 자리와 작은 `m/s` 단위로 표시한다.
- 유효한 속도를 한 번도 받지 못했다면 `—`, 이동 상태는 `확인 전`이다. 단, 연결 문제가 있으면 현재 확인 불가가 우선한다.
- 속도 freshness는 motion 자체의 age로 판단한다. 토픽 수신만 계속된다고 무효 숫자를 최신 값으로 취급하지 않는다.
- 유효한 motion이 없거나 오래되면 이전 유효 값을 `마지막 수신 값` 배지·수신 시각과 함께 회색으로 표시할 수 있다. 현재 이동 상태는 `현재 확인 불가`다.
- 이전 세션의 수치는 현재 motion으로 승계하지 않는다. 새 세션에서 motion을 받기 전에는 `—`를 표시한다.
- 최신 유효 값에서 선속도 또는 절대 각속도가 기준 이상이면 `이동 중`이다. 선속도만 기준 미만이면 `회전 중`을 보조 표시한다.
- 두 값 모두 기준 미만일 때만 `정지 상태`다.
- 유효하게 수신한 0은 `0.00 m/s`이며, 미수신을 0으로 치환하지 않는다.

고정 안내 문구:

> 주행 정보 기준 추정값입니다. 정지 상태가 순찰 완료, 고장, 원격 정지 성공을 뜻하지는 않습니다.

**속도 0을 순찰 완료·정지 명령 성공으로 해석하지 않는다. 이동 상태와 명령 결과는 별도의 정보다.**

### 3.7 최근 알림

- 시각·중요도·내용을 최신순으로 표시한다. 종류는 연결·문제 발생·수신 재개·제어 결과다.
- 같은 문제는 key를 기준으로 지속 중 한 번만 생성한다. 복구 시 지속 중 표시를 해제하고 복구 알림을 한 번 추가한다.
- Bridge 지연에서 끊김으로 심각도가 바뀌면 같은 활성 연결 문제를 갱신한다. 매초 새 알림을 만들지 않는다.
- Bridge 연결 문제 중에는 토픽별 파생 지연 알림을 새로 만들지 않는다. 복구 후 실제 토픽 상태로 다시 평가한다.
- 첫 토픽 수신 대기 중에는 설정된 토픽 지연 기준까지 유예하고, 계속 미수신이면 해당 문제 알림을 한 번 생성한다. 행 상태는 미수신을 유지한다.
- 새 Bridge 세션에서는 이전 세션의 활성 토픽 문제를 종료 처리하고 새 이력으로 평가한다. 아직 새 데이터를 받지 않았다면 수신 재개라고 기록하지 않는다.
- 최대 100건을 유지하고 초과 시 가장 오래된 항목부터 제거한다. 활성 문제 중복 방지용 상태는 표시 이력과 별도로 유지한다.
- 알림이 없으면 `최근 알림이 없습니다`를 표시한다. 데모 알림은 실제 서버 알림과 분리한다.

## 4. 화면과 디자인

### 4.1 실제 수신 화면 `/`

1440px 데스크톱 너비를 기준으로 다음 순서로 구성한다.

1. 상단: `LIMBO 관제`, `LIMBO-01`, 연결 상태, 마지막 서버 수신
2. 조건부 안내 띠: 연결 확인 중·지연·끊김·서버 갱신 불가
3. 핵심 요약: 추정 이동 속도 카드, 이동 상태 카드
4. 본문 왼쪽: 데이터 수신 상태 / 오른쪽: 로봇 제어
5. 하단: 최근 알림

- 최대 컨테이너 폭은 padding 포함 1440px, 중앙 정렬, 데스크톱 좌우 여백 56px, 섹션 간격 24px다.
- 본문 비율은 약 2:1로 수신 상태를 넓게 배치한다. 1000px 미만에서는 세로 배치한다.
- 700px 미만에서는 요약 카드도 세로 배치하고 좌우 여백을 16px로 줄인다. 표는 행 카드로 바꿔 정보가 잘리지 않게 한다.
- 데이터 표의 열은 `항목 / 수신 상태 / 마지막 수신 / 수신 빈도`다.
- 행 순서는 주행 정보, LiDAR 원본, LiDAR 필터 결과, 카메라 원본이다.
- 표 하단에는 수신 상태가 센서 정상 여부가 아니라는 설명과 적용된 토픽별 지연 기준을 표시한다.
- 카메라는 수신 상태만 제공한다. 썸네일·영상 영역·원본 다운로드를 만들지 않는다.
- 운영 화면에 ROS2 토픽명·API명·개발 인계 메모를 넣지 않는다.
- 실제 화면에는 `실제 수신 · 제어 미연동` 표시를 사용하고, 데모 화면으로 가는 링크를 명확히 구분한다.

### 4.3 접근성

- 색상 외에 텍스트와 아이콘으로 상태를 전달한다.
- 키보드 포커스, hover, 비활성화, 처리 중 상태를 제공한다.
- 상태 변화는 `role=status`, 중요한 연결 장애는 `role=alert`로 알린다. 매초의 숫자 갱신을 반복 낭독하지 않는다.
- 처리 중에는 `aria-busy`, 비활성 사유는 연결된 설명 텍스트를 사용한다.
- 모달은 포커스 가두기·복귀, Esc 닫기를 지원한다. 초기 포커스는 취소 버튼이다.
- 불필요한 숫자 애니메이션을 넣지 않고, 처리 중 회전 표시도 reduced-motion 설정을 따른다.

## 5. 제어 데모와 실제 제어의 경계

### 5.1 실제 화면

세 버튼을 배치하지만 모두 비활성화하고 다음 안내를 표시한다.

> 실제 로봇 제어는 아직 연결되지 않았습니다. 제어 동작은 데모 화면에서 확인할 수 있습니다.

ROS2 명령 발행·서비스 호출·프로세스 재시작 기능을 구현하지 않는다. 실제 화면에서 임의 타이머로 성공 결과를 보여 주지 않는다.

### 5.2 데모 화면 `/demo`

- 상단에 `데모 데이터 · 실제 로봇을 제어하지 않습니다`를 항상 표시한다.
- 실제 공급자와 Mock 공급자는 공통 화면 상태 인터페이스를 구현하되 저장소와 이벤트 흐름은 분리한다.
- 데모 시나리오 도구는 운영 UI와 시각적으로 구분한다.
- 시나리오: 정상 수신, 일부 토픽 지연, Bridge 수신 지연, 연결 끊김, 최초 접속, 서버 연결 문제.
- 명령별 다음 결과를 성공·명시적 거절·응답 없음·응답 후 상태 확인 없음 중에서 선택할 수 있게 한다.
- 시나리오를 초기화하면 기존 데모 타이머와 진행 요청을 취소하여 이전 결과가 새 화면에 섞이지 않게 한다.

### 5.3 명령 흐름

```text
요청 전송 → 로봇 응답 → 상태 확인
```

각 단계는 대기·진행 중·완료·실패·확인 불가를 별도로 표시한다. 요청 ID, 요청 시각, 결과 설명을 버튼 근처에 유지한다.

| 명령 | 처리 중 | 상태 확인 완료 | 명시적 실패 | 응답·확인 부족 |
|---|---|---|---|---|
| 원격 정지 | 정지 요청 중 | 정지 상태 확인됨 | 정지 요청 실패 | 정지 여부 확인 불가 |
| 순찰 재개 | 재개 요청 중 | 재개 확인됨 | 재개 실패 | 재개 여부 확인 불가 |
| 프로그램 재시작 | 재시작 중 | 재시작 확인됨 | 재시작 실패 | 재시작 여부 확인 불가 |

- `request_id`를 생성하고 응답·상태 확인 이벤트를 같은 ID로 연결한다. 이전 요청의 이벤트는 무시한다.
- 요청 전송 단계는 비동기로 완료한다. 데모 로봇 응답은 전송 완료 후 0.5초, 상태 확인 이벤트는 응답 후 1초에 발생한다.
- 응답 대기와 상태 확인 제한 시간은 각각 5초다. 데모 설정으로 변경할 수 있게 한다.
- 클릭, 전송 완료, 로봇 응답 수신만으로 최종 성공을 표시하지 않는다.
- 명시적 거절은 실패다. 응답 없음·상태 확인 없음·중간 연결 끊김은 확인 불가다.
- 최종 상태 이후의 지연 이벤트가 결과를 조용히 성공으로 바꾸지 않게 한다.
- 요청 중 세 버튼 모두 비활성화한다. 재연결 후 미완료 명령을 자동 재전송하지 않는다.
- 결과는 다음 요청 전까지 유지하고 최근 알림에 한 번 남긴다.
- 연결 상태가 연결됨이 아니면 모든 버튼을 잠그고 `연결을 확인한 후 사용할 수 있습니다`를 표시한다.
- 재개는 데모의 `patrolling` 및 `has_resumable_task`로 허용 여부를 판단한다. 이미 순찰 중·재개할 작업 없음·상태 미확인은 각각 사유를 표시한다. 속도로 이 값을 추정하지 않는다.

원격 정지는 빨간색 전체 폭 주 버튼, 순찰 재개는 청록 외곽선 보조 버튼, 프로그램 재시작은 별도의 관리 영역에 둔다.

재시작 확인 모달:

- 제목: `프로그램을 재시작할까요?`
- 설명: `현재 작업이 중단되고 프로그램이 다시 실행됩니다.`
- 추가 안내: `데모 동작이며 실제 프로그램을 재시작하지 않습니다.`
- 버튼: `취소`, `재시작`

### 5.4 후속 실제 제어의 필수 조건

| 명령 | 후속 구현에서 필요한 근거 |
|---|---|
| 정지 | 명령 ID에 대응하는 로봇 응답, 정지 제어 상태, 명령 이후의 최신 주행 정보 |
| 재개 | 로봇 응답과 순찰 상태의 재개 전환. 속도 상승만으로 성공 판정 금지 |
| 재시작 | 명시된 대상 프로세스의 실행 인스턴스 변경 및 준비 완료. Bridge 재연결만으로 성공 판정 금지 |

데모의 확인 이벤트는 이런 상태 보고가 존재한다고 가정한 예시다. 실제 로봇에서 검증된 기능으로 설명하지 않는다. 실제 제어 대상과 ROS2 인터페이스는 후속 개발에서 별도 확정한다.

## 6. 구현·검증·완료 기준

### 6.1 구현 순서와 독립 검증

1. 공통 계약을 읽고 수신 모델·상태 판정·시간 계산의 자동 테스트를 작성한다.
2. 서버 API와 ROS2 없이 실행 가능한 가상 송신기를 구현한다.
3. 목업을 참고해 실제 수신 화면을 구현하고 가상 송신기로 장애 시나리오를 검증한다.
4. 별도 Mock 공급자로 제어 데모를 구현한다.
5. 실제 Bridge를 연결해 통합 검증하고 실행 문서를 작성한다.

가상 송신기는 정상·일부 토픽 중단·전체 토픽 중단·전송 중단·새 세션·중복·역순·잘못된 요청을 재현한다. 개발용 도구로 표시하며 실제 로봇 정보인 것처럼 소개하지 않는다.

### 6.2 인수 시나리오

| 시나리오 | 기대 결과 |
|---|---|
| 최초 접속 | 수신 기록 없음, 속도 `—`, 확인 전, 토픽 미수신 |
| 정상 수신 | 네 항목 수신 중, 시각·빈도·추정 속도 갱신 |
| LiDAR 필터 결과만 중단 | Bridge 연결됨 유지, 해당 토픽만 지연, 문제 알림 한 건 |
| 전체 토픽 중단 | Bridge 연결됨 유지, 토픽만 지연·미수신 |
| Bridge 중단 | 마지막 수신 후 3초에 지연, 10초에 끊김 |
| 서버 중단 | 브라우저에 서버 갱신 불가, 이전 연결됨을 현재 상태처럼 표시하지 않음 |
| 복구·서버 재시작·새 Bridge 세션 | 최신 전체 상태로 복구, 이전 세션 이력을 현재 상태로 승계하지 않음 |
| Gazebo 정지·시간 역행 | 음수 경과 시간 없음, Bridge 연결과 토픽 정지를 구분 |
| 유효한 속도 0·회전 | 0.00 표시, 회전 구분, 순찰 완료·정지 명령 성공 표시 없음 |
| 무효 속도·오래된 값 | 현재 값으로 취급하지 않음, 보존 값에는 마지막 수신 표기 |
| 중복·역순·잘못된 요청 | 상태 및 heartbeat 오염 없음, 계약에 맞는 응답 |
| 제어 데모 3종 × 결과 4종 | 단계별 피드백, 실패와 확인 불가 구분, 결과·알림 유지 |
| 실제 화면 | 제어 비활성화, 실제 명령 전송·가짜 성공 없음 |
| 반응형·접근성 | 1440·1024·768·390px에서 정보 접근 가능, 키보드로 데모·모달 조작 가능 |

- 시간 제어 테스트로 임계값 직전·정확한 경계·직후를 검증한다.
- 브라우저 테스트로 실제/데모 분리, 연결 장애, 중복 클릭, 늦은 결과, 모달 포커스를 확인한다.
- 목업과 1440px 화면을 시각적으로 비교한다. 좁은 화면의 잘림·수평 넘침·숫자 갱신 흔들림도 확인한다.
- 정상 로컬 환경에서 ROS2 수신 정보가 2초 이내 화면에 반영되어야 한다.
- README에는 서버·UI 설치, 개발·빌드·실행·종료, 설정, 실제/데모 주소, 가상 송신기, 통합 검증 절차를 작성한다.
- 검증하지 못한 실제 ROS2·화면·성능 항목을 완료로 보고하지 않는다.

## 7. 계약 변경과 개발용 프롬프트

공통 계약 변경은 [Bridge PRD](../../relay_prog/docs/PRD.md)를 먼저 수정한다. Bridge 직렬화·테스트 수신 서버와 Dashboard 검증 모델·가상 송신기·양쪽 계약 테스트를 함께 갱신한다. 화면 상태·문구·임계값의 기준 문서는 이 PRD다.

```text
dashboard/docs/PRD.md를 기준으로 LIMBO Dashboard 서버와 UI만 구현해줘.
공통 수신 계약은 relay_prog/docs/PRD.md를 읽고 그대로 따라줘.
적용되는 저장소 지침을 확인하고 코드는 dashboard/ 아래에 작성해줘.
기존 limbo/와 relay_prog/ 프로그램 코드는 변경하지 마.

FastAPI 서버와 React/TypeScript UI를 만들고, 1440px 목업을 참고해줘.
Bridge 연결, 토픽별 수신, 브라우저의 서버 연결 문제를 구분해줘.
미수신은 —, 데이터 도착은 수신 중으로 표시하고 센서 정상이라고 쓰지 마.
속도 0을 순찰 완료나 정지 명령 성공으로 판단하지 마.

실제 화면의 제어는 비활성화하고 /demo에서만 가상 제어를 제공해줘.
요청 전송 → 로봇 응답 → 상태 확인을 나누고,
실패·응답 없음·상태 확인 없음과 늦은 결과를 검증해줘.
실제 데이터와 데모 데이터·알림·결과를 섞지 마.

ROS2 없는 가상 송신기로 독립 검증하고 실제 Bridge 통합도 확인해줘.
설치·실행·설정·테스트 방법을 README에 작성해줘.
완료 보고에는 변경 내용, 실행 명령, 테스트 결과와 미검증 항목을 구분해줘.
```
